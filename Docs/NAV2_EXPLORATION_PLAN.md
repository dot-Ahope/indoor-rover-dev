## 2. 단계 계획

### N1 — 좁은 공간 주행 신뢰성 (1~2세션) ← 최우선
사무실의 실제 좁은 구간을 반복 통과할 수 있어야 탐사가 성립한다.

1. **`allow_reversing: true`** — 360° 라이다라 후진 안전. 갇힘 상황에서 180° 회전 없이 이탈 가능.
2. **MPPI 컨트롤러 시험** (`nav2_mppi_controller` 설치됨) — 샘플링 기반이라 좁은 공간·후진·장애물 근접에서 RPP보다 강함. **리스크: CPU** → 벤치마크로 RPP(튜닝판)와 비교 후 채택 결정.
3. **복구동작 재구성** — 현재 spin(스윕 φ60cm)이 좁은 곳에서 상황을 악화시킴. backup 우선, spin은 공간 확인 후. BT 커스터마이즈.
4. **벤치마크 코스 확정·측정** — 사무실 실제 좁은 구간 S자 왕복. **게이트: 5/5 무개입 통과.**
5. (4 실패 시) **Smac Lattice 플래너 도입** — NavFn은 로버를 원으로 취급. 직사각 풋프린트(0.5×0.33)는 **방향에 따라 통과 가능 폭이 다르므로**, 방향 인지 계획(Smac Lattice, diff 모델)이 좁은 틈에서 본질적으로 유리. 단 도입 비용이 있어 벤치마크 실패 시에만.

### N1.5 — 저고도 장애물 대응 (권장)
- **D455f depth → costmap 투입** (STVL 또는 voxel layer). 라이다가 못 보는 낮은 물체를 카메라 depth로 회피.
- 카메라를 유지하기로 한 결정이 여기서 활용됨. **리스크: CPU** → depth 해상도/주기 낮춰 투입.
- 게이트: 라이다에 안 걸리는 낮은 상자를 회피하는지.

### N2 — 사무실 전체 수동 매핑 (1세션)
- 조이스틱으로 전 구역 매핑 → 맵 저장 (기존 절차 보유).
- 탐사(N3)는 온라인 slam을 그대로 쓰므로 이 맵은 **기준선·비교용** (탐사 결과 맵과 대조해 커버리지 평가).

### N3 — 프론티어 탐사 레이어 (2~3세션) ← 핵심 신규 개발
"로봇청소기처럼 전부 탐사" = **frontier exploration**: 기지/미지 경계(frontier)로 반복 이동하며 맵을 완성.

- **`rover_exploration` 패키지 직접 구현** (프로젝트 취지: 직접 구축·설명 가능):
  1. `/map`에서 프론티어 검출 (free↔unknown 경계 클러스터링)
  2. 후보 선정 (거리·크기 가중) → `NavigateToPose` 전송
  3. 실패한 프론티어 **블랙리스트** (P6 물리 한계 수용 장치)
  4. 프론티어 소진 → 맵 저장 → 시작점 복귀
- 대안(폴백): m-explore-ros2 포팅판. 직접 구현이 막히면 전환.
- **배터리 게이트**: `/battery` 전압 임계 미만 시 탐사 중단·복귀 (P5 대응).
- 게이트: 방 1개 완전 탐사 → 사무실 전체.

### N4 — 통합·자동화 (1세션)
- `full.launch` + systemd: 부팅 → 스택 자동 기동. 탐사는 별도 트리거.
- 자율주행 중 foxglove 자동 off (P4).
- 메트릭 기록: 커버리지 곡선(시간별 맵 면적), 개입 횟수, 소요 시간 — 정량 비교 데이터.

### N5 (선택) — 커버리지 주행
- "전부 가보기(탐사)"를 넘어 **"바닥 전부 훑기"**가 필요해지면 `opennav_coverage`(왕복 패턴) 검토.
- 현재 목표 문구("전부 탐사")는 N3로 충족된다고 해석. 필요 시 확장.

#### 5.x 컨트롤러 판정 확정 (2026-09-07 벤치마크, 스케일 교정 후)
- **RPP 채택.** 3전 3승(19.7s/25.1s/10.7s, 경로효율 ~1.0, 반전 0). MPPI 2전 2패(목표 0.37m 앞 진동, |v| 평균 0.016) + 벽 접촉 사고.
- MPPI 실패 원인(근거는 `Docs/debug_log/2026-09-07/SUMMARY.md` "MPPI 원인 분석"):
  ① 제자리 회전 모드 부재 → U턴을 반경 v_max/ω_max = 0.21m 호로 수행 → 횡변위 ~0.4m (실측 ±0.31/0.32) → 1.1m 통로 여유(0.33m) 초과
  ② 목표 0.4m 이내에서 경로 크리틱 일괄 OFF → Goal(5)+GoalAngle(3) 만 남아 장애물 비용과 평형 → 정체
  ③ 직사각 풋프린트(반대각 0.37m) + consider_footprint → 벽 근처 회전 샘플 전부 충돌비용 → 직진 미세이동만 생존 → x 진동·y 고정
  ④ 예측 지평 1.6s×0.08 = 12.8cm (Nav2 기본 설계 ~1.4m) — 0.08 m/s 플랫폼과 구조적 불일치
  ⑤ 샘플링 노이즈 vx_std 0.05/vx_max 0.08 (62%), wz 79% → 경계 클리핑 → 지령 급변 6배
  ⑥ CPU 는 아님 (20Hz 유지, 미달 3회/5400)
- 재도전 조건: 사전 회전 BT + 크리틱 문턱 재설정 + 노이즈 축소 + 지평 확대 + 원형 풋프린트 — 5개 이상 결합 변경 필요. **N4 이후로 보류.**

## 6.x 스톨 감지 실측 결론 (2026-09-07) — 근본 원인은 PWM 50Hz
- 받침대 실험(`Docs/debug_log/2026-09-07/`): 구속 휠의 FG 가 PWM 주기 펄스를 냈던 원인은 **모터 PWM 이 50Hz(구모터 값)로 남아 있던 것**(이관 계획 T1 미적용). **20kHz 전환 후** 구속 시 펄스 0 → 600ms 감지·자동복구·3회 래치 정상, 자유 휠은 10~100mm/s 전 구간 1s 내 정확 추종(duty ≈ 0.36+4.5v 선형).
- 결정: 펌웨어 스톨 정책 유지(검증 완료). Jetson `stuck_monitor` 는 **보조**(트랙 슬립·벽 밀림 등 휠이 도는 갇힘)로 N1.5 에 배치.
- **N1 전 재실측 필수**(모두 50Hz 조건 측정치였음): 바닥 데드밴드(승격값 확정), 줄자 스케일(VX_SCALE 0.783 재측정), 최고속(MAX_LINEAR_SPEED 0.10 상향 여부), 회전 slip 계수. Nav2 속도 파라미터는 그 뒤 갱신.

## 5. 컨트롤러 선택 판단 (2026-09-02, 실측 기반)

### 시스템 특성 (판단 근거)
① 초저속(0.10 m/s — 10Hz 제어로 충분) ② 기동 데드밴드(ω<~0.15 rad/s 무반응, RPP 데드락으로 실증)
③ 회전 슬립(실회전≈명령의 40~60%) ④ 직사각 풋프린트+좁은 사무실(여유 40~80cm) ⑤ CPU 빠듯(향후 VIO·YOLO로 심화)

### 결론
- **1순위 MPPI (저속 사양: controller_frequency 10Hz + batch 튜닝)** — 실패 지점(좁은 공간·후진·풋프린트)을 정면 해결.
  감시 항목: (a) 소속도 출력이 데드밴드에 걸려 정체하는지 (b) 회전 슬립 모델 불일치로 회전 지연.
  → **N1 벤치마크(S자 5/5)가 채택 게이트.**
- **RPP는 폴백/개활지용 유지** (CPU 거의 무료, 트인 공간 검증). DWB 제외(현재속도 창 샘플링 = 데드밴드와 상성 최악).
  Smac Lattice 는 벤치마크 실패 시에만.

### 컨트롤러 무관 시스템 개선 (펌웨어 백로그 — 어떤 컨트롤러든 이득)
1. **데드밴드 보상**: 최소기동 미만 명령을 최소값으로 승격 (특성② 근본 제거)
2. **회전 슬립 피드포워드**: 실회전/명령 ≈0.5 보상 (특성③ 제거 → MPPI 모델 정확화)
3. (기존) 휠별 텔레메트리 — 위 둘과 **같은 펌웨어 작업 세트**로 묶어 진행 권장

### 미래 스택(VIO·YOLO·depth) 영향
- 주로 GPU 부하라 컨트롤러 선택은 불변. 단 CPU 여유를 추가로 깎음(합계 ~0.5~1코어 추정)
  → **VIO 도입 시점 = "CPU 벽" 트리거 발동 가능성 高** → 그때 conditioner(45%) 정리 실행
  (VSLAM 도입으로 conditioner 역할이 재편되는 시점과 일치 — 선제 최적화를 안 한 기존 판단과 정합).
- VIO 로 localization 향상 → 허용오차 축소·정밀 기동 여지 → 미세 기동에 강한 MPPI 이점 증가.

## 6. 기동 데드밴드 보상 — 평가와 추가 작업 분석 (2026-09-03)

### 6.1 현재 보상값(0.020) 평가
**근거 데이터**: 기동 임계 ≈ 0.012~0.016 m/s(휠속도). 0.012는 불규칙(정지마찰 경계), 0.016·0.020 신뢰 가능 (§debug_log/2026-09-03).
- **적절성: 적절.** 임계 상한(0.016) 대비 +25%, 하한 대비 +67% 마진. 위험이 비대칭 — 너무 낮으면 자율주행 중 간헐 데드락(치명), 너무 높으면 미세 위치결정만 거칠어짐(경미) → 높은 쪽으로 오차를 두는 게 맞음.
- **분해능 비용**: 휠 [0.003, 0.020) 구간 지령이 전부 0.020으로 실행. 순수회전 환산 |ω|<0.163 rad/s 는 모두 0.163으로. Nav2 실용상 문제 없음 (RPP rotate 0.5 rad/s, 15cm 허용오차에 2cm/s 접근이면 충분).
- **한계 두 가지**: ① 고정값 → 전압(12.0V 이하)·바닥(카펫)·트랙장력 변화에 마진이 잠식됨 ② 하한 방식 → 정지마찰 > 운동마찰인데도 "움직인 뒤"의 저속 능력을 못 씀.

### 6.2 데드밴드 보상 외 — 현재 문제(좁은 공간 Nav2)를 푸는 추가 작업
| 층 | 작업 | 효과 | 비용 | 우선 |
|---|---|---|---|---|
| 펌웨어 | **기동 보조(적응형)**: 목표>0인데 FG=0이 ~100ms 지속 → 순간 MIN으로 킥 → FG 움직이면 실제 목표로 복귀 | 저속 분해능 보존 + 전압·바닥 자동 적응. 고정 하한의 두 한계 동시 해소 | 중 (safety_monitor 스톨 감지와 구분 필요) | ★1 |
| 펌웨어 | **전압 연동 하한**: MIN_eff = MIN×V_ref/V_batt (/battery 이미 측정) | 최대 변동 요인(전압) 보상 | 소 (한 줄) | ★1 |
| 펌웨어 | **저속 속도추정 개선**: 펄스 카운트 → 펄스 주기 기반 (저속에서 FG 펄스 희소·양자화 → PID 채터링 의심) | 저속 제어 자체가 좋아져 유효 데드밴드 축소 가능 | 중 (speed_controller 확인 필요) | 2 |
| 펌웨어 | **회전 슬립 피드포워드**: 실ω≈0.35×지령(일관 실측) → 차동항 보정 | MPPI DiffDrive 모델 정합 → 좁은 공간 궤적 판단 개선 | 중 (odom 슬립계수 재도출·V_MAX 상호작용) | 2 |

### 6.3 권장 순서
1. **재벤치마크(★0)** — 데드밴드 하나로 얼마나 회복됐는지 먼저 계량. 결과가 나머지 투자를 결정.
2. **다음 펌웨어 묶음(★1)**: 기동 보조 + 전압 연동 하한 + 휠별 텔레메트리 — 한 번의 플래시. 슬립 피드포워드는 벤치마크에서 MPPI 모델 불일치가 실제 병목으로 보이면 추가.
3. **Jetson 접촉 감지 모니터(★1)** — 컨트롤러와 독립, 사각 안전.
4. **트랙 장력 점검(★1, 비용 0)** — 가능하면 벤치마크 전에.
