# nvblox 이전 계획 (2026-09-09 수립)

## 0. 결정

**현재 스택(Nav2 + STVL)을 먼저 완성하고, 그 다음 Isaac ROS nvblox 로 이전한다.**

Jetson Orin Nano 를 쓰고 있으므로 GPU 를 놀리는 것은 낭비이고, TSDF/ESDF 를 GPU 에서 만드는
nvblox 가 이 하드웨어에 더 맞는다는 판단. 다만 **이전 자체가 목적이 아니라 성능 향상이 목적**이므로,
비교 기준선을 수치로 고정한 뒤 A/B 로 판정한다.

> 상자와 52cm 어긋난 빈 자리를 세고 있었다. 로버를 세워 두고 60초 잰 결과(job209)

> 문제로 다시 나타난다.

## Phase S — 현재 스택 개선 (이전 전 완료 조건)

### S1. STVL 감쇠 시간 확정 — 진행 중

`voxel_decay` 15.0 → 30.0 적용, 검증 대기.

- 근거: job167 에서 깊이점 소실(t=4, 카메라~상자 0.45m)부터 로버가 상자를 완전히 지날 때
  (t≈26)까지 약 22초 필요한데 15초에 만료(t=19) → 계획 여유 −1.4cm, 최근접 0.4cm.
- **종료 조건**: 로버가 상자를 완전히 지날 때까지 `lc_box` 유지, 실제 최근접 ≥ 5cm.

### S2. 카메라 사각지대 축소 ★ 이전 전 필수

`camera.launch.py` 의 `decimation_filter.filter_magnitude 4` 재검토 (→ 2 또는 off).

- 근거: job167 에서 깊이점이 **카메라~상자 0.51m → 0.45m 구간에서 142 → 0 으로 급락**했다.
  job71 실측 최소 측정거리 0.22~0.25m 보다 **훨씬 멀다**. 640×480 에 디시메이션 4 를 걸면
  유효 해상도가 160×120 이 되고, 디시메이션은 최소 측정거리를 키운다.
  **즉 사각지대를 우리가 스스로 넓혀 놓았다.**
- 대안: RealSense advanced mode(`json_file_path`) 의 disparity shift 로 최소거리 축소.
  `obstacle_range` 가 1.2m 뿐이라 최대거리를 내줄 여유가 있다.
- **측정**: 깊이점이 끊기는 카메라~물체 거리 / 포인트 수 / CPU 증가분.
- **종료 조건**: 끊김 거리 ≤ 0.35m, 그리고 CPU 증가가 `ekf_node` 의
  "Failed to meet update rate" 재발을 유발하지 않을 것.

### S3. 동적 장애물 망각 검증

상자 제거 시험. `decay_acceleration`(현 3.0) 튜닝.

- **종료 조건**: 상자 제거 후 로버가 그 구역을 절두체 안에서 다시 볼 때 소거되고,
  전역 코스트맵에 유령이 남지 않을 것.

### S4. 회피 주행 반복 검증

같은 코스 3회 연속.

- **종료 조건**: 접촉 0/3, 완주 3/3, 계획 좌우 전환 0, 직진 중 ω 부호반전 ≤ 1.0회/m,
  실제 최근접 ≥ 5cm.

### S6. CPU 여유 확보 ★ 2026-09-09 추가 — 우선순위 높음

`ekf_node` 의 주기 위반이 주행 정지의 뿌리로 확인됐다(§8.16).
CPU 부족 → EKF 지연 → `odom→base` TF 지연 → slam 이 스캔을 전부 폐기 → `map→odom` 미발행
→ `map→base_link` 조회가 tf2 버퍼(10초) 만료와 함께 실패 → 주행 중단.

- 최대 소비원: `sensor_conditioner` 35~37% (200Hz IMU 를 파이썬으로 중계).
  `gyro_fps` 인하는 **불가** — D455 자이로가 100Hz 프로파일을 지원하지 않는다(실측).
  → 컨디셔너에서 다운샘플하거나 C++ 로 옮긴다.
- `foxglove_bridge` 는 `viz:=lean` 으로 크게 줄었으나 클라이언트 접속 시 다시 오른다.
  측정 주행 중에는 끄는 것을 검토.
- **종료 조건**: 주행 30초 동안 `Failed to meet update rate` 0회,
  `Message Filter dropping` 0회, load < 6.

## Phase N — nvblox 이전

### N1. 환경 조사 (코드 변경 없음)

- JetPack 버전 확인 → 호환되는 Isaac ROS 릴리스 확정 (Isaac ROS 는 JetPack/CUDA 조합에 민감).
- `isaac_ros_common` 개발 컨테이너를 쓸지, 네이티브 설치가 가능한지 판정.
  현재 우리는 **네이티브 Humble + micro-ROS 에이전트만 컨테이너**다. 이 구조를 지킬 수 있는지가 핵심.
- **판정 게이트**: 현재 스택(펌웨어·EKF·SLAM·Nav2)을 건드리지 않고 nvblox 만 추가할 수 있는가.
  아니라면 이전 범위와 위험을 다시 산정한다.

### N2. nvblox 단독 기동

Nav2 에 연결하지 않고 TSDF/ESDF 생성만 확인.

- 입력: `/camera/camera/depth/image_rect_raw` + `camera_info` (nvblox 는 포인트클라우드보다
  깊이 이미지를 선호한다 — 이 경우 우리 포인트클라우드 파이프라인 일부가 불필요해진다).
- **측정**: GPU 사용률·전력·온도, ESDF 갱신 주기, 메모리.
- **판정 게이트**: 15W 모드에서 열·전력 여유가 있고, 배터리 주행 시간이 실용적일 것.

### N3. Nav2 코스트맵 연결

`nvblox_nav2` 코스트맵 레이어로 STVL 을 대체. **라이다 `obstacle_layer` 는 유지**한다
(레이어 분리 원칙: 센서는 자기가 감지할 수 있는 것만 지운다 — 09-09 §8.6).

- 설정은 **두 레이어를 모두 남기고 `plugins` 목록으로 전환**한다.
  재빌드 없이 A/B 가 가능해야 한다.

### N4. A/B 비교

S5 기준선과 **같은 코스·같은 스크립트**로 측정.

### N5. 채택 판정

- 채택: CPU 여유가 늘고 회피 지표가 동등 이상.
- 기각: STVL 로 복귀(`plugins` 한 줄). 브랜치는 기록으로 남긴다.

## Git 전략

### 브랜치

```
main
 └─ feature/wt600-migration   ← 현재. Phase S 를 여기서 마무리
      │
      └─(S5 완료 후 병합)──▶ main   + 태그 stvl-baseline
                               │
                               └─ feature/nvblox-migration   ← Phase N
                                    │
                                    └─(N4 통과 시)──▶ main
```

- **S5 전에는 main 에 병합하지 않는다.** 지금 스택은 오늘 하루에 링크·코스트맵·컨트롤러를 모두
  건드려 아직 검증 중이다. 검증이 끝난 상태만 main 에 올린다.
- **태그 `stvl-baseline`** 이 nvblox 실패 시 돌아올 지점이다. 태그 없이 브랜치만으로는
  "그때 그 설정" 을 재현하기 어렵다.
- **nvblox 는 반드시 별도 브랜치.** Isaac ROS 는 빌드 환경·의존성이 크게 바뀔 수 있어,
  실패 시 main 이 오염되면 안 된다.
- `feature/wt600-migration` 은 병합 후 삭제한다(오늘 시점 미푸시 커밋이 쌓여 있으므로
  병합 전에 반드시 push).

### 커밋 규칙 (오늘 방식 유지)

- **원인 1건 = 커밋 1개.** 메시지에 근거 수치를 넣는다(무엇을 재서 그렇게 판단했는지).
- **기각한 가설도 커밋에 남긴다.** 오늘 소거 계열 가설 3건을 기각한 기록이
  이후 판단의 근거가 되었다.
- **정정은 새 커밋으로.** 이전 커밋의 결론이 틀렸으면 지우지 말고 정정 커밋에 무엇이
  왜 틀렸는지 쓴다(오늘 `f1a76d8`, `35e0c12`, `dd519f6` 가 그 예).
- **비밀번호 스캔은 diff 가 아니라 '결과 내용' 을 본다.**

  ```bash
  git grep --cached -l "<금지 문자열>" | wc -l    # 0 이어야 커밋
  ```

  `git diff --cached | grep -c` 는 틀린 방법이다 — **삭제된 줄(`-`)까지 세므로**,
  비밀번호를 제거하는 커밋에서 오탐이 난다(2026-09-09 실제로 이 오탐 때문에 게이트가
  막혀 amend 가 안 됐다). 반대로 이 잘못된 검사를 게이트로 걸지 않고 출력만 하면
  유출을 그대로 커밋하게 된다 — 같은 날 그 사고도 냈다. **검사는 반드시 게이트로 건다.**

### Phase N 의 추가 규칙

- **환경 구성(N1)은 코드와 분리해 커밋**한다. Isaac ROS 설치·버전 고정은 되돌릴 일이 많다.
- nvblox 설정은 STVL 설정을 **지우지 말고 나란히 둔다**. `plugins` 목록만 바꿔 A/B.
- N2 이후 각 단계마다 `tegrastats` 로그를 `Docs/debug_log/` 에 남긴다.
  GPU·전력은 사후 재현이 어렵다.

## 2026-09-14 재검토 — 목표가 "경로 추종" 이 아니라 "로봇청소기형 자유 이동" 이면 판단이 달라진다

사용자 지적: 최종 목표는 로봇청소기처럼 공간을 스스로 다니는 것이며, 계획된 경로만 따르는 구조(차선 변경 → 모서리 정체, 09-14 §2.18)로는
그 성능에 다가갈 수 없다. 09-11 판정은 "경로 추종 스택의 실패 원인이 지도 계층이 아니다" 였고 그것은 여전히 사실이지만, 목표가 바뀌면
**지도 계층에 요구하는 것**이 바뀐다. 여러 각도에서 다시 본다. (근거: `Docs/debug_log/2026-09-14/SUMMARY.md` §2.5~§2.18)

### 1. 오늘 스택이 지도 계층에서 땜질한 것 — nvblox 는 이것을 구조로 가진다

| 오늘의 문제 | 오늘의 처리 (휴리스틱) | nvblox 의 처리 (구조) |
|---|---|---|
| 상자 실루엣 비산점(프레임당 2~4점, 고립 99 %)이 셀을 켬 | 릴레이: 5 cm 복셀 <3점 제거 | TSDF **가중 통합** — 한 프레임의 고립점은 가중치가 낮고 다른 프레임의 자유공간 관측이 덮어쓴다 |
| 카메라 0.36~0.38 m 근거리 아티팩트가 진로 0.6 m 앞에 자취를 남김 | 릴레이: 카메라 <0.45 m 제거 | 통합 최소거리 파라미터 + 광선 따라 자유공간 carving(가림 인식) |
| 절두체 근평면(min_z 0.55) 안쪽은 소거 불가, 감쇠 30/60 s 로만 지움 | voxel_decay 30 → 60 s | **광선 기반 자유공간 갱신** — "보이는데 비어 있다" 를 프레임마다 반영, 시간 감쇠에 의존하지 않음 |
| 상자 셀이 실물보다 1~2셀 넓음(낮은 가장자리 점 + 5 cm 반올림) | min_obstacle_height 0.08 시도 → 기각 | **ESDF 거리장** — 셀 비용이 "가장 가까운 표면까지 거리" 에서 나오므로 inflation 층의 계단 비용이 아니라 연속 거리. 격자 자체는 남는다(복셀 0.05; Orin Nano 에서 0.03 가능 여부는 측정) |
| 마킹/소거 규칙이 mark_threshold·decay·frustum 세 파라미터에 얽힘 | 값 하나씩 실험 | 파라미터가 "센서 모델·통합 거리·복셀 크기" 로 정리됨 |

즉 09-11 트리거 (a) "절두체 clearing 이 실제 실패를 만든다" 는 **오늘 충족됐다**(근거리 자취는 절두체가 못 지우고, 릴레이로 우회했다).
(b) CPU: STVL 자체는 병목이 아니지만 릴레이 42 ms/프레임(한 코어 0.6)이 새로 붙었다 — nvblox(GPU) 가 릴레이와 STVL 을 함께 대체하면 CPU 는 오히려 준다. (c) N1 은 아직.

### 2. D455f 와의 궁합 — "최적화" 의 실제 의미
- NVIDIA 의 nvblox 참조 파이프라인은 RealSense D435i/D455 (+cuVSLAM) 로 문서화·튜닝돼 있다(`isaac_ros_nvblox` realsense 예제, `realsense_splitter` 로 에미터 on/off 분리). 우리 D455f(IR 필터판)의 깊이는 동일 계열이라 그대로 적용된다.
  입력은 점군이 아니라 **depth 이미지 + camera_info** 라 대역폭·변환 비용이 준다(지금은 14k 점군을 15 Hz 로 릴레이 → STVL).
- 그러나 **센서 물리는 바뀌지 않는다**: 사각지대 0.40 m, 실루엣 혼합 화소, 저해상 640×480×15 는 그대로다. nvblox 가 하는 것은 그 잡음을 시간·공간 가중으로 눌러 주는 것이지 없애는 것이 아니다. 근거리 사각은 여전히 "기억" 으로 메워야 한다(nvblox 도 마지막 관측을 유지한다 — 다만 광선 소거가 있어 STVL 보다 덜 낡는다).
- 라이다(2D)는 nvblox 의 일급 입력이 아니다(3D 라이다는 지원). 좌측 물체·벽은 지금처럼 Nav2 ObstacleLayer(라이다)를 옆에 두면 된다 — 오늘 구조(STVL+ObstacleLayer)와 같은 2층.

### 3. nvblox 가 고치지 않는 것 — 오늘 정체의 직접 원인
- 입구 정체의 기전(차선 변경 heading +15~30°, RPP 둘레 LETHAL 검사, 속도-검사거리 결합)은 **컨트롤러·행동** 계층이다. RPP 를 그대로 두고 지도만 nvblox 로 바꾸면 같은 자리에서 같은 이유로 선다(상자 셀이 0.5~1셀 덜 넓어져 여유가 몇 cm 늘 뿐).
- 자세: nvblox 는 TF 를 믿는다. slam_toolbox 의 map→odom 점프(18~36 cm 관측)가 map 프레임 TSDF 를 번지게 하므로 **odom 프레임 로컬 지도**(반경 밖 소거)로 써야 한다.
- 격자 양자화는 복셀 크기로만 준다(0.05 → 0.03 이면 CPU/GPU ×4.6). Orin Nano(8 GB, 1024 CUDA) 에서의 통합·ESDF 시간은 **측정 전까지 추정치**(AGX 벤치 3~4 ms/프레임의 4~6 배 → 15~25 ms 로 15 Hz 는 될 것으로 추정).

### 4. 목표의 정확한 정의(사용자 정정): **경로 추종은 유지하되, 경로 추종으로 자유 공간을 자유롭게 이동**하는 것
청소기형 이동이란 "경로를 버린다" 가 아니라 "커버리지 경로처럼 장애물 옆 차선 변경·회전이 잦은 경로를 **막힘 없이** 따른다" 는 뜻이다.
오늘의 입구 정체(차선 변경 → 모서리 heading +15~30° → RPP 둘레 검사)는 그런 경로에서 **매번** 일어날 실패 모드이므로, 이것을 없애는 것이 최종 목표의 전제다.
세 계층이 각각 할 일:
- **계획**: NavFn 8-연결 격자는 곡률을 모르고 대각선으로 붙는다. 운동학적 계획(Smac Hybrid-A*: 최소 회전반경·비용 인식)이나 SimpleSmoother 로
  차선 변경을 **더 일찍·완만하게** 시작해 모서리에서의 heading 을 줄인다. 이것이 정체의 직접 원인(자세)을 건드리는 유일한 계층이다.
- **컨트롤러**: RPP 는 carrot 추종이라 경로 옆 장애물을 모른다(둘레 LETHAL 검사로 멈출 뿐). **MPPI** 는 경로를 추종하면서(PathFollow/PathAlign critic)
  장애물 비용(ObstaclesCritic)을 함께 최적화해 **경로를 국소적으로 비켜 지나간다** — "경로 추종으로 자유 이동" 에 정확히 해당하는 컨트롤러다.
  이미 `FollowPathMPPI` 로 설정만 돼 있고(N1 벤치마크 후보), 오늘 코스트맵으로도 벤치마크할 수 있다.
- **지도**: Smac 도 MPPI 도 셀의 이진 마킹+inflation 계단보다 **연속 거리장(ESDF)** 을 받을 때 여유를 정량적으로 다룬다. nvblox 는 "지금 문제의 해법" 이
  아니라 **위 두 계층이 제대로 동작하기 위한 지도**다. 낮은 물체(상자 0.14 m, 라이다 0.185 m 아래)를 3D 로 기억하고 광선으로 지우는 것도 그 경로들에서 필수다.

### 5. 판정 — "의미 없다" 에서 "측정으로 결정한다" 로
09-11 의 "지금 단계에서 이전하지 않는다" 를 **철회**하고 Phase N 을 재개한다. 단, 순서와 게이트는 지킨다:
1. **N0 (신설, 1일, 현재 스택 무손상)**: Jetson 에 isaac_ros_nvblox 설치(N1 환경 조사 포함) → RealSense 예제로 **정지 측정** —
   같은 상자 배치에서 (i) 상자 가장자리가 물리(+0.11)에서 몇 셀 안에 잡히는가(오늘 STVL+릴레이 +0.13~+0.21) (ii) 릴레이 없이 비산점·근거리 자취가 남는가(job311/312 기준을 nvblox ESDF 슬라이스에 그대로 적용)
   (iii) GPU/CPU 부하와 통합 주기(15 Hz 유지?) (iv) 복셀 0.03 가능 여부. 통과 기준: (i) ≤1셀, (ii) 0/450 프레임급, (iii) 15 Hz·CPU 한 코어 미만.
2. N0 통과 시 N2~N3: **로컬 코스트맵의 STVL 만** `nvblox_nav2` 층으로 교체(odom 프레임, 라이다 ObstacleLayer 유지), 전역은 그대로. 같은 코스로 A/B(N4).
3. 계획·컨트롤러는 nvblox 와 독립으로 먼저: **Smac Hybrid-A*(또는 SimpleSmoother)** 로 차선 변경의 곡률을 완만하게, **MPPI 벤치마크**(현재 코스트맵으로 가능)로
   경로 추종 중 국소 회피. 같은 중앙 상자 코스에서 "모서리 도달 시 heading" 과 "정지 횟수" 를 지표로 RPP+NavFn 과 A/B. nvblox 는 이들이 쓰는 거리장을 좋게 하는 두 번째 단계.
   **09-14 정지 A/B 결과(09-14 §2.19)**: Smac R0.10/cost1.2 + 통로선 목표에서 모서리 heading 7.7°(NavFn 18.7°)·상자 여유 0.40(0.38) — 우세하나 파라미터·목표 위치에 매우 민감
   (R0.20 루프 4.3 m, R0.05 반대편 우회 4.96 m). 그리고 **전역 코스트맵의 상자가 정지 중에도 10 cm 씩 움직인다**(SLAM map→odom 흔들림 × STVL 90 s 누적) — 전역 계획 입력 자체가 흔들리므로
   계획기 교체보다 앞서 지도 프레임 문제를 풀어야 한다(전역 감쇠 30 s / odom rolling 전역 / nvblox odom 단일 지도). 이것이 nvblox(odom 프레임 로컬 지도) 쪽 근거를 하나 더 보탠다.
4. 이전 뒤에도 남는 것: 근거리 사각 0.40 m(카메라 물리), 2D 라이다 층, RPP 를 쓰는 동안의 입구 정체(→ 컨트롤러 교체로만 해소).

### 6. N1 환경 조사 결과 (2026-09-14, 읽기 전용 — job316 + 공식 문서)
- Jetson: L4T **R36.5.0**(2026-01-16 빌드, JetPack 6.2 계열), Ubuntu 22.04.5, 커널 5.15.185-tegra, CUDA **12.6**(driver 540.5), docker 29.3 + nvidia-ctk 설치됨,
  디스크 193 GB 여유, RAM 7 GB 중 5 GB 가용. Isaac ROS 저장소·패키지 흔적 없음. Nav2 apt 패키지에 smac/mppi/smoother 모두 있음.
- 공식 릴리스 노트: **Isaac ROS 3.2**(2024-12, Humble, JetPack 6.1/CUDA 12.6) → **3.2 Update 1**(2025-01, **JetPack 6.2 지원**). 4.0(2025-10)부터는
  Jetson Thor·JetPack 7·Ubuntu 24.04 로 넘어갔고 최신 4.6(2026-08) 문서는 Orin Nano 를 지원 목록에 올리지 않는다.
  → 우리 조합(Humble + JetPack 6.2.x + CUDA 12.6)은 **Isaac ROS 3.2 Update 1** 이 맞는 버전이다. 문서상 "Orin Nano 4 GB 는 메모리 부족" 경고만 있고
  8 GB 는 지원 목록(0.30 부터). nvblox 성능 수치는 AGX Orin 기준(0.05 m 복셀: TSDF 0.8 ms·ESDF 1.7 ms/프레임) — Orin Nano 는 측정해야 한다.
- 설치 경로: 3.2 는 `isaac_ros_common` 개발 컨테이너(docker, JetPack 6 태그) 또는 apt(`isaac.download.nvidia.com/isaac-ros/release-3`, 저장소 등록 필요 — 루트 URL 은 404, 문서의 설정 스크립트로 등록).
  **sudo 가 필요하므로 실행 전에 사용자에게 고지한다.** 컨테이너 방식이면 호스트 ROS 와 분리되어 현재 스택(네이티브 Humble)을 건드리지 않는다 — N0 에 적합.
- nvblox 입력은 depth 이미지 + camera_info(+색), 3D 라이다 선택. RealSense 는 예제에 일반 명사로만 등장(D455 개별 명시는 없음) — 같은 realsense2_camera 드라이버 토픽이라 문제 없음.
  Nav2 연결은 nvblox 의 코스트맵 플러그인(ESDF 2D 슬라이스) — 플러그인 클래스명은 N2 에서 소스로 확인.

기각하지 않는 이유를 요약하면: 오늘 하루 지도 계층에서 한 세 가지 땜질(릴레이 두 규칙·감쇠 연장)이 모두 nvblox 가 구조로 가진 기능이고,
청소기형 이동으로 목표를 옮기면 컨트롤러가 요구하는 지도(연속 거리장·광선 소거·3D)가 STVL 의 설계 범위를 벗어나기 때문이다.
채택하지 않을 이유가 남는다면 그것은 **Orin Nano 의 부하**와 **설치 구조(N1)** 뿐이며, 둘 다 N0 에서 측정된다.
