## 1. 증상
- 09-17 §15.4 · §15.5: 상자 옆 통과(mp9 · mp11 · mp12)에서 로컬(odom) 코스트맵의 상자 좌측 끝을 그 순간 map→odom 으로 map 에 옮기면, 같은 시각 전역(map) 코스트맵 상자보다 **로버 쪽(+y)으로** 있었다. 상자 옆 구간:

  | mp11 (t 13~24) | +0.032 → +0.057 m | **+7.3 ~ +8.3 cm** | 14 / 11 |
  | mp9 (t 14~25) | +0.039 → +0.060 m | **+0.7 ~ +3.2 cm** | 9 / 10 |

  데이터: [`2026-09-17/outputs/j426_boxframes.txt`](../debug_log/2026-09-17/outputs/j426_boxframes.txt)(도구 [`job426_boxframes.py`](../debug_log/2026-09-17/jobs/job426_boxframes.py), bag `2026-09-17/bags/bag_mp9~12.tgz` 로컬 보관). 표의 범위는 출력 원문 행(t 13.0 · 15.4 · 18.4 · 20.8 · 23.8 등)과 맞는다(이 카드 작성 때 대조).
- 결과: 로컬 코스트맵 기준 상자 여유가 1.4~2.6 cm 로 작게 나왔고(09-17 §13.4), mp10 · mp12 의 **Optimizer fail** 은 로컬 여유 3.0 cm 순간에 났다(09-18 §12.2 → [간헐 중단 카드](intermittent-abort-dy.md)). 같은 순간 전역(map) 기준 측면 간격은 셀 8~11 cm · 물리 13~15 cm 였다(09-17 §15.5).
- 09-17 의 설명(그때): "통과하면서 SLAM 이 odom 의 횡 위치를 3~8 cm 씩 보정(yaw 보정은 −0.2~−1.6° 뿐) → 주로 차선변경 중 odom 이 횡이동을 덜 셈 — **스키드스티어 옆미끄럼 추정**, … 미확인". 그리고 상자는 옆을 지나는 동안 카메라에 안 보이므로(mp12 미관측 23.8 s) 로컬은 '보였을 때 odom 좌표로 찍어 둔 복셀(decay 120 s)' 을 쓰고, 그동안의 odom 드리프트만큼 상자가 로버 쪽에 남는다(이 기전 설명 자체는 이후에도 유지).

## 4. 조치와 효과
- **보정값**: 데크 yaw −2.68° = −0.04677 rad. 근거 = 정지 2 회(2.667 · 2.686) · 동적 1 회(2.69, **버그판**) 평균 2.681°. 수정판 동적 2.57 을 넣으면 평균 2.641° — 차이 0.04° 로 결정에 영향 없음(이 카드 계산).
- 카메라 위치는 데크 원점(= 라이다 중심, base (0.152, 0)) 기준 오프셋 (0.080, 0.0475) 을 같이 회전: x = 0.080·cos − 0.0475·sin(−2.68°) = 0.08213, y = 0.080·sin + 0.0475·cos = 0.04371 → (0.23413, 0.04371). 회전 중심이 실제 고정점과 다르면 수 mm 차(무시, §9.3).
- **효과(전 → 후)**: 거리 비례 옆 보정 b +0.036~+0.051 → −0.009~+0.001 m/m(dy1~dy6 −0.015~+0.001) · map→odom 옆 오프셋 끝으로 +5.7~+8.6 cm → ±2 cm · 로컬−전역 상자 좌측 끝 차(옆 구간) +0.7~+8.3 → dy1 +0.2~+1.3 / dy2 −0.5~−2.3 / dy4 +0.0~+1.0 cm · 로컬 상자 최소 여유 1.4~2.6 → 2.5~5.1 cm(dy1~dy6) · 복귀 회전 자리 여유 3.0 → 4.1~10.2 cm.
- **영향 범위(§9.3)**: TF 를 쓰는 노드(SLAM · costmap · depth_relay · EKF)는 자동 반영. π 를 하드코딩한 **옛 오프라인 분석 도구**(job370 · job415 등 `LYAW = π`)는 옛 bag 분석용으로 그대로 둠 — **09-18 이전 bag 을 새 URDF 로 재생하거나, 이후 bag 을 옛 도구로 분석하면 2.68° 가 섞인다.** 같은 날 만든 job439 · 441 · 441b · 441c 는 `π − 0.04677` 을 하드코딩.
- **현재 코드 확인(2026-10-30, 이 카드 작성 시)**: `ros2_ws/src/rover_description/urdf/rover.urdf` 의 세 관절 값이 위와 같고, `Docs/02_hardware/rover.urdf` 와 줄 끝(CR) 말고는 **동일**. `stuck_monitor.py:32 LIDAR_YAW = math.pi − 0.04677`, `rf2o_gate.py:35` 기본 `lidar_yaw = math.pi − 0.04677`(이후 시기에 생긴 두 번째 사본). 실행 시 `description.launch.py` 는 기본으로 `rover.urdf` 를 읽고 xacro 는 `use_xacro:=true` 일 때만.
- ⚠ **xacro 는 rover.urdf 와 같지 않다**(이 카드 작성 시 발견, 기록 없음): xacro 기본 `deck_x` = **0.000**(rover.urdf 는 0.152), `cam_dx` = **0.0822**(rover.urdf 는 0.080 으로 회전). `deck_yaw` 인자는 −0.04677 로 맞다. 즉 `use_xacro:=true` 로 띄우면 라이다 · 카메라 x 위치가 15 cm 어긋난다. 09-18 배포 확인(job433)의 xacro 줄이 전부 '-'(정규식 불일치)라 이 차이를 그때 못 봤다(§10 job433). 지금 기본 실행 경로에는 영향 없음.

### job431_odomdrift.py ★ 보정 분해
- 실행: Jetson, `python3 job431_odomdrift.py BAG GOAL_EPOCH [T_END] [BAG GOAL_EPOCH [T_END] …]`(T_END 는 §11 에서 추가 — 다음 인자가 `/` 로 시작하지 않으면 T_END).
- 왜: 09-17 §15.5 의 '옆미끄럼' 가설을 회전량 대 거리로 가르려고.
- 하는 일: `/tf` 에서 map→odom(SLAM)과 odom→base_link(EKF)를 모은다. **(수정판)** map→odom 은 (stamp, 수신 순번)으로 정렬 후 같은 stamp 는 마지막 값만. 보정 시점 = 직전 보정 대비 0.5 mm 또는 0.01° 넘게 바뀐 곳. 연속 보정 (a, b) 마다: 시각 t1 의 odom 자세 p 를 옛 보정 a 와 새 보정 b 로 각각 map 에 옮겨 차 (dx, dy) 를 **옛 map heading** 기준으로 앞 δf · 옆 δl(+왼쪽) 분해, δψ = 두 보정 yaw 차. 같은 구간 odom 이 센 거리 Δs(odom→base 궤적 길이)와 회전 Δψ. 주행별: 합 δf · δl · δψ, Δs 합, Σ|Δψ|, 회귀 **δl = a·Δψ + b·Δs**(절편 없는 최소제곱, R²), c = Σ(Δψ·δψ)/ΣΔψ², 직선(|Δψ| < 2°)/회전 구간의 δl/m. 통합: 같은 회귀 + Δψ 만 · Δs 만 단독 회귀, 왼회전(Δψ > +2°) · 오른회전 · 직선별 Σδl 과 δl/rad · δl/m.
- 해석 문구(코드): δl ∝ Δψ → 옆미끄럼, δl ∝ Δs · 회전 무관 → 방향 오차 누적, δψ ∝ Δψ → 회전 스케일 오차, δf ∝ Δs → 전진 스케일 오차.
- 출력: `j431_odomdrift.txt`(mp9~12, 버그판) · `j436_drift_window.txt`(T_END, 버그판 + dy1 · dy2) · `j437_dedup.txt` 첫 절(수정판 6 회) · `j435_dy*_verify.txt` B 절(dy1 · dy2 는 버그판, dy3~6 은 수정판 — 보정 횟수 25~31 회로 수정판 범위).
- 쓰인 곳: §9.1(옆미끄럼 기각), §10 · §11.2 · §11.3 기준 ②, §13.1 'b' 열.
- 결함: (버그판) 같은 stamp 이중 발행으로 보정 두 번 셈(§5.2). 옆 보정 '합' 은 회당 ≈1 cm 흔들림이 누적돼 잡음이 큼 — 판정은 b 로. 보정 사이 odom 이동량이 작은 구간(직선 0.05 m 등)의 δl/m 은 불안정(dy5 '직선 −0.044 (0.05 m)').
- 다시 쓸 수 있나: 수정판은 그대로 쓸 수 있다(map→odom 이 `/tf` 에 있는 bag). 상시 도구로 옮겨지지 않음.

## 10. 용어
- **장착 yaw 오차**: 센서가 URDF 에 적힌 방향보다 z 축으로 더 돈 각. 여기선 데크가 −2.68°(위에서 볼 때 시계 방향)로 돌아 있어, 공칭 TF 로 옮긴 점들이 실제보다 +2.68° 돌아가 보였다(옆벽이 +2.67° 로 기울어 보임).
- **URDF joint rpy**: 고정 관절의 `<origin xyz="…" rpy="roll pitch yaw"/>`. 부모(base_link) 좌표에서 자식(센서) 좌표로의 변환. yaw 를 바꾸면 RSP 가 내는 `/tf_static` 이 바뀐다.
- **TF static · RSP**: URDF 고정 관절은 `robot_state_publisher` 가 `/tf_static`(transient_local)으로 한 번 발행한다. URDF 를 바꾸면 RSP 를 다시 띄워야 하고, RSP 가 두 개 떠 있으면 서로 다른 값을 낼 수 있다(§9 job434).
- **게걸음 각(crab angle)**: map(SLAM)에서 본 로버 **진행 방향 − 몸체 방향**. 스키드스티어가 제대로 굴러가면 0. 센서 장착 yaw 오차 e 가 있으면 SLAM 이 몸체 방향을 e 만큼 틀리게 알아 **회전 · 곡률과 무관하게 −e 로 일정**하게 나온다.
- **옆미끄럼(side-slip)**: 트랙이 옆으로 미끄러져 몸체가 몸체 y 방향으로 움직이는 것. 스키드스티어는 회전할 때 생기므로 회전량에 비례하고 회전 방향에 따라 부호가 바뀐다. EKF 가 휠 vy = 0 을 강하게(σ 1 cm/s) 믿으면 못 센다.
- **SLAM 보정 분해**: map→odom 이 바뀌는 순간(= SLAM 이 odom 을 고치는 순간)마다 로버 위치가 얼마나 옮겨졌는지를 몸체 기준 앞(δf) · 옆(δl) · 방향(δψ)으로 나눈 것. 옆 보정 합이 '주행 동안 odom 이 옆으로 틀린 양'.
- **거리 비례분 b**: 회귀 δl = a·Δψ + b·Δs 의 b(m/m). 장착 yaw 오차 크기 |e| 면 b ≈ tan|e| — 2.68° 면 0.047(부호는 오차 방향에 따름, 여기선 +). 합계보다 잡음에 강하다.
- **벽 맞춤 yaw(wall-fit yaw)**: 몸체와 나란하다고 알고 있는 벽(옆면을 붙인 벽)을 센서 점으로 직선 맞춤해 얻은 각. 0 이 아니면 그만큼이 장착 오차. RANSAC 으로 바깥 점을 버리고 인라이어로 SVD(주성분) 방향을 잡는다.
- **RANSAC**: 무작위 두 점으로 직선 후보를 만들고 가까운 점(인라이어)이 가장 많은 후보를 고르는 방법. 벽 옆의 다른 물체 점을 버리는 데 쓴다.
- **map→odom 이중 발행**: slam_toolbox 가 map→odom 을 20 Hz 로 보내되 stamp 는 10 Hz 로 갱신해, 같은 stamp 의 메시지가 둘이고 보정 순간엔 두 값이 다르다(옛 값 → 새 값). 분석은 같은 stamp 의 **마지막 수신값**만 쓴다(CLAUDE.md §6).
- **로컬(odom) vs 전역(map) 코스트맵**: 로컬은 odom 좌표에 장애물을 찍어 두므로 odom 이 틀어지면 기억된 장애물이 로버에 대해 밀린다. 전역은 map 좌표라 SLAM 보정을 따라간다.
