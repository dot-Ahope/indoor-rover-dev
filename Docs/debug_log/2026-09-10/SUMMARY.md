# 2026-09-10 — 관측 도구가 관측 대상을 망가뜨리고 있었다. 그리고 "감쇠" 는 "물러짐" 이었다

## 0. 이 날의 결론

두 가지를 배웠고, 하나는 스스로 정정한 것이다.

1. **관측 도구가 관측 대상을 망가뜨리고 있었다.** Foxglove Studio 클라이언트가 붙어 있는 것만으로
   1 코어 가까이 먹어 EKF 를 굶기고 주행을 실패시켰다(§4). 이후 측정 주행은 브리지를 끄고,
   경로·코스트맵은 rosbag 으로 남겨 **사후에** 본다.
2. **`voxel_decay` 를 "얼마나 오래 기억하는가" 로만 보다가 틀렸다.** 코스트맵에서 비용이
   내려간다는 건 **장애물이 물러진다**는 뜻이다. 내접 비용(발행값 99) 아래로 떨어지면 그 셀은
   통과 불가가 아니라 '비싼 길' 이 되고 플래너가 파고든다. job198 에서 `lc_box` 가 99→79→69 로
   내려가는 것을 나는 "감쇠가 잘 동작하는 증거" 로 읽었으나, 그것이 바로 **로버가 상자 옆을
   지나는 동안 상자가 녹고 있던** 장면이었다(§7 정정). 로컬을 **영속(−1)** 으로, 전역을 **90초**로
   바꾸자 같은 코스에서 접촉 없이 완주했다(§8, 육안 확인).

그리고 job205 가 드러낸 것: 이 장면에서 카메라는 **출발 0.9초 뒤부터 상자를 전혀 보지 못한다**.
회피는 37초간 순수하게 **기억만으로** 성립했다. "감쇠 30초면 충분" 이라는 S1 의 결론은
상자를 계속 본다는 전제에 기대고 있었다.

## 2. decay_acceleration — 장면 의존성을 없앴다 (job183 → job184)

job183 에서 또 접촉했다. 시계열:

```
t=5 깊이점 174 lc_box 100 → t=6 깊이점 0 lc_box 100 → t=8 lc_box 0 (2~3초 만에)
t=11 깊이점 423 lc_box 100 (다시 보이자 복구) → t=14 lc_box 0
```

`voxel_decay 30` 인데 2~3초 만에 사라진다. t=8 시점 카메라~상자 중심은 **0.580 m** 로
`min_z 0.55` 를 **넘어** 절두체 '안' 이었고, 가속 감쇠가 지웠다.

**핵심: 깊이점이 끊기는 거리가 장면마다 다르다.** 09-09 는 0.45~0.51 m, 오늘은 0.65 m.
심지어 job183 t=10~12 에는 116 → 423 → 44 로 되살아났다 사라졌다 한다.
**`min_z` 를 한 값으로 맞추는 접근 자체가 취약하다** — 09-09 에 0.25→0.55 로 올린 것도
그 장면에서만 맞았던 것이다.

**조치**: `decay_acceleration` 3.0 → **0.0**. 절두체 안팎을 가리지 않고 모두 `voxel_decay`
동안 균일 유지 → '관측이 끊기면 30초 유지' 규칙이 장면에 의존하지 않는다.
대가: 치운 물체도 최대 30초 남는다(0.08 m/s 로 2.4 m 이동분, 로컬 3×3 m 롤링이라 지나가면 소멸).
동적 망각 튜닝은 S3 에서 따로 한다.

**결과(job184)**: 로컬이 상자를 잃은 샘플 147 → **12**, 계획이 접촉 경로였던 비율 48% → **0%**,
실제 최근접 0.0 → **45.6 cm**.

## 3. stuck_monitor — Nav2 액션 상태는 전이 시점에만 발행된다

job184 는 접촉 없이 진행했으나 0.92 m 에서 CANCELED 됐다.

```
RegulatedPurePursuitController detected collision ahead! → follow_path 중단
behavior_server: Running backup → "backup completed successfully"   ← 복구는 성공
stuck_monitor: 지령 11.2cm/9° 인데 관측 1.4cm/6.0° (비율 0.13) → 목표 취소
```

**복구가 성공한 직후 stuck_monitor 가 취소했다.** 09-09 에 넣은 억제 로직이 막았어야 했다.

원인: **Nav2 액션 서버는 상태를 전이 시점에만 발행한다**(연속 발행이 아니다).
`EXECUTING` 을 받을 때마다 `recovery_until = now + W(2.0s)` 로 갱신하는 방식이었는데,
후진 복구가 4.5초 걸려 보류 창이 복구 도중 만료됐다.

```
backup 시작(EXECUTING) 994.3 → recovery_until 996.3
backup 완료            998.8   (그 사이 EXECUTING 재발행 없음)
stuck 발동            1000.17  ← 이미 만료
```

**조치**: `recovery_active` 플래그 도입 — EXECUTING 이면 세우고, 종료 상태(4/5/6)를 받으면
내린 뒤 W 만큼 더 보류한다. 판정은 `recovery_active or now < recovery_until` 일 때 건너뛴다.

> 중간에 `ros2 node info /stuck_monitor` 의 구독 목록에 상태 토픽이 없어 "구독 자체가 안 됐다"
> 고 판단했으나 **오독**이었다. `_` 로 시작하는 숨김 토픽은 기본 출력에서 빠진다.
> `ros2 topic info /backup/_action/status` → `Subscription count: 1` 로 확인.

## 4. ★ 진짜 병목 — Foxglove 클라이언트 연결

stuck_monitor 를 고쳐 재기동했는데 Nav2 가 **기동 실패**했다.

```
planner_server 는 설정 성공(플러그인 전부 초기화, 코스트맵 리사이즈 완료)
lifecycle_manager: Failed to change state for node: planner_server.
                   Exception: planner_server/get_state service client: async_send_request failed.
load 6.35, EKF 위반 86회, slam 폐기 28회
```

설정 오류가 아니라 **부하 상태에서 서비스 응답이 늦어 생긴 타임아웃**이다.
CPU 상위를 보니 `foxglove_bridge` 69.6% — 부팅 직후엔 상위권에 없던 것이다.

```
ss -tn | grep :8765
  ESTAB  192.168.0.101:8765  ←  192.168.0.6:65351     ← 사용자 PC 의 Foxglove Studio

foxglove_bridge 정지 후 30초 재측정:
  EKF 주기 위반 : 0 회  (직전 86회)
  slam 스캔 폐기: 0 회  (직전 28회)
  Nav2 전 노드 active   (직전 기동 실패)
```

`viz:=lean` 으로 토픽을 줄여도 **클라이언트가 붙으면** 브리지가 1코어 가까이 쓴다.
09-09 주행 중 Foxglove 로 경로를 보고 있던 것이 EKF 를 굶겨 TF 를 끊고 주행을 망친
인과에 포함된다 — **관측 도구가 관측 대상을 망가뜨리고 있었다.**

**운용 규칙**: 측정 주행 중에는 Foxglove Studio 창을 닫는다(또는 브리지를 내린다).

   조향 부호반전 1.1회/m

**사후 검토 대상으로 남은 관측 2건** — bag 으로 확인할 것:

1. **t=11~13 에 로컬·전역이 동시에 0** 이었다가 깊이점이 331개로 되살아나자(t=13) 복구.

   지워진 것인지, 다른 이유인지는 bag 을 열어 봐야 갈린다.

> bag 은 `Docs/debug_log/<날짜>/bags/` 에 두고 **git 에는 넣지 않는다**(주행 1회당 10~15MB).
> `.gitignore` 에 규칙 추가. 보존이 필요한 주행은 그때 `git add -f` 로 의도적으로 넣는다.

## 7. 계측 결함과 수정 — 상자를 map 에 한 번만 고정하면 안 된다 (job196 → job198)

### job196 — 지표가 통째로 무의미해졌다

```
깊이점: 최대 0, 최소 0   ← 주행 내내 상자 사각형 안 깊이점이 하나도 없다
① 실제 최근접 0.0 cm (접촉?)  ② 계획 최소 여유 −2.4cm
```

출발 시 검출(≥40점 필요)은 성공했는데 그 직후부터 끝까지 0이다. 상자를 **출발 시 map 좌표에
한 번만 고정**하는 방식의 결함이다 — SLAM 이 `map→odom` 을 보정하면 고정 좌표와 실물이 어긋난다.
그 시점 실측 보정량 **11.6 cm(−0.081, 0.083, −1.2°)**, 상자 폭은 18 cm 다.
이 주행은 목표 1.60 m 인데 2.24 m 를 주행하며 회전이 많았다.

→ **job196 의 ①·⑤ 는 신뢰할 수 없다.** "최근접 0.0cm = 접촉" 도 계측 산물일 수 있다.
   bag(15MB/61.3s/8504)은 남겼으므로 사후 확인 대상.

### 수정 — 보일 때마다 재고정

`detect_box()` / `make_peri()` 로 분리하고, 주행 중 **0.5초마다 재검출해 위치를 갱신**한다.
직전 위치에서 `REFIX_MAX 0.30 m` 이내일 때만 채택한다(다른 물체로 튀는 것 방지).
안 보이면 마지막 관측을 유지한다 — 우리가 관심 있는 '안 보이는 구간' 만 외삽이 되고
나머지는 항상 최신이다. 지표 ⑥(마지막 관측 이후 경과 초)을 추가해 **외삽 구간을 드러낸다.**

### job198 — 지표는 좋았으나 **실제로는 접촉했다**

```
결과 SUCCEEDED   주행 1.71m   29.4초
③ lc_box 최소 69 / gc_box 최소 75 — 전 구간 유지, 0 으로 안 떨어짐
   값이 99 → 79 → 69 로 서서히 내려간다 = voxel_decay 선형 감쇠가 눈에 보인다
⑥ 상자 미관측 최대 28.3초 — 그동안 마킹이 버텼다
② 계획이 접촉 경로였던 샘플 0/295 (0%), 최소 여유 12.5cm
④ 경로 좌우 전환 0회,  조향 부호반전 0.6회/m
① 실제 최근접 11.5cm
```

`voxel_decay 30초`인데 주행이 29.4초 — **만료 직전에 완주**했다. 설계가 의도대로 맞물렸다.

**⑥ 이 드러낸 것**: 상자를 주행 시작 직후 한 번 보고 그 뒤 28.3초 동안 못 봤다.
즉 ① 의 11.5 cm 는 **28초 묵은 관측의 외삽**이고, `map→odom` 보정이 11.6 cm 규모였으므로
**오차가 측정값과 같은 크기**다. 재고정 로직이 있어도 안 보이면 갱신할 수 없다 — 원리적 한계.
→ **접촉 여부의 최종 판단은 실물 관측**이다. 과정 지표(②③④·조향)는 상자 추정에 덜 민감하고
   전부 양호하므로, 그쪽을 1차 근거로 쓴다.

> ⚠ **정정 (같은 날 늦게)**. 위 판단은 틀렸다. 사용자 육안 관찰:
> "상자를 잘 피해 가다가, 상자가 로버 우측 측면에 오는 순간, 제자리에서 회전하여
>  박스에 가까운 쪽으로 경로를 틀고, 박스를 치고 지나가면서 목적지에 도착했다."
>
> 데이터로 되짚으면 t=18 에 계획 횡좌표가 +0.411 → +0.202 로 꺾이고 같은 순간 RPP 가
> 제자리 회전(v=0, ω=−0.320)했다. 그때 `lc_box` 는 99 → 79 → **69** 였다.
>
> 내가 "값이 99→79→69 로 서서히 내려간다 = 감쇠가 눈에 보인다" 를 **좋은 신호로 읽은 것이
> 오독**이다. 코스트맵에서 비용이 내려간다는 건 **장애물이 물러진다**는 뜻이다.
> 내접 비용(발행값 99) 아래로 떨어지면 그 셀은 통과 불가가 아니라 단지 '비싼 길' 이 되고,
> 플래너는 파고든다. **로버가 상자를 지나는 20~30초가 곧 상자가 녹는 시간이었다.**
> "만료 직전에 완주했다 = 설계가 의도대로 맞물렸다" 도 같은 오독의 연장이다 —
> 만료 전이라도 **이미 충분히 물러져 있었다.**

### 이 주행이 실제로 증명한 것

카메라는 **t=0.90 s 이후 상자를 한 번도 보지 못했다** — 깊이점 관측 10/382 샘플.

즉 **이 회피는 37초간 순수하게 기억만으로 성립했다.**
30초 감쇠였다면 t≈31 에 99→69 로 녹아 job198 과 같은 파고들기가 재현됐을 구간이다.
S1 에서 "감쇠 30초면 충분하다" 고 정한 것은 **상자를 계속 본다는 전제**에 기대고 있었고,
그 전제가 이 장면에서는 성립하지 않는다.

### 남은 불확실성

- **① 37.1 cm 는 측정이 아니라 외삽이다.** 마지막 관측이 t=0.90 이므로 그 뒤 거리는 계산값이다.
  `map→odom` 보정이 11.6 cm 규모(§7)이므로 오차가 작지 않다. 접촉 여부의 최종 판정은
  **육안 관찰**이고, 이번 건은 사용자가 "실제로 상자에 닿지 않았다" 로 확인했다.
- **영속 마킹은 동적 망각을 포기한 것이다.** 이 상자는 라이다에 안 잡히므로 카메라 마킹을
  지울 수단이 사실상 없다. 로컬은 창을 벗어나며 잊지만(0.08 m/s 로 약 19초),
  전역은 90초를 기다려야 한다 → **S3 에서 별도 검증**.
- S4 종료 조건은 **3회 연속**이므로 이 1회로는 미달. job196 은 계측 무효, job198 은 접촉이라
  카운트는 여기서 새로 시작한다. **현재 1/3.**

### 부수적으로 고친 것

- 재부팅 후 `base.launch`(micro-ROS 에이전트)를 빠뜨려 보드 토픽이 전멸했다.
  `/wheel_odom` 없음 → EKF 입력 0 → `odom→base` TF 없음 → local_costmap 타임아웃 →
  `controller_server` 가 activate 를 못 끝냄. **"Nav2 활성화가 느리다" 로 보였지만 뿌리가 끊긴 것.**
  처음엔 USB 재열거로 `docker --device` 가 끊긴 것으로 추정했으나, 사용자가 재부팅했다고
  알려주어 **단순 누락**으로 확정. 재부팅 후 점검 순서는 base → sensors → slam → nav2.
- 재부팅으로 `/tmp` 가 비워져 작업 스크립트가 전부 사라졌다(`run_xfer_all.sh` 로 재전송).
- Windows 에서 만든 스크립트의 **CRLF** 가 그대로 올라가 원격 bash 가 `$''` 을 명령으로
  읽고 통째로 깨졌다. `run_j.sh` 가 **전송 전에** `tr -d ''` 하도록 고쳤다.

## 9. ★ 계측이 벽을 상자로 보고 있었다 — ①②③⑤⑥ 전면 무효

### 발단

복귀 주행(job207)에서 로버가 상자를 쳤다(사용자 확인). 코스트맵에 상자가 lethal 로

상자가 없었다.** "영속(-1)으로 바꿨는데도" 였다.

### 결정적 측정 — 로버를 세워 두고 60초 (job209)

job205 CSV 를 다시 보니 로버가 **전혀 움직이지 않은** t=0~1.5 구간에 상자 깊이점이
84→54→64→32→42→105→228→146→27→2→0 으로 요동치다 사라졌다.
거리가 안 변했는데 사라졌으므로 "가까워져서 화각을 벗어났다" 로는 설명되지 않는다.
로버를 세워 둔 채 **base_link 기준**(SLAM 무관) 고정 창의 깊이점을 60초 쟀다:

### 원인 — 클러스터링 없는 median (job125_avoid3.py detect_box)

```python

이 범위에는 상자만 있는 게 아니다. 클러스터링으로 나눠 보면(job210):

```

**벽의 y 와 상자의 x 를 조합한 빈 자리**에 사각형이 생긴다. 그 안의 깊이점이 0 이 되는 것은
당연하다. 상자와 **52 cm** 어긋나 있었다.

## 11. 삭제 정책 — 우리 선택과 업계 방향

사용자 제안: *"센서를 벗어나 인식하지 못하게 되면 지우는 것이 아닌, 계속 기억하게 만들고,
멀리 떨어지거나 다시 센서로 인식했을 때 없는 경우만 지운다."*

이는 점유 격자의 제1원칙과 같다 — **관측 실패와 부재는 다른 사건**이고, 표준 구현들은
free / occupied / **unknown** 세 상태를 두어 unknown 을 free 로 강등하지 않는다.

| 방식 | 안 보이면 | 지우는 조건 | 가림 처리 | 대표 |
|---|---|---|---|---|
| 레이캐스팅 | 유지 | 레이가 관통한 셀만 | ✅ 자동 | Nav2 costmap_2d |
| 베이지안 로그오즈 | 유지 | 관통 시 확률 감소 + clamping | ✅ | OctoMap |
| TSDF weight | 유지 | 관측 시 SDF 갱신 | ✅ 부분적 | Voxblox, nvblox |
| **절두체 + 시간감쇠** | 감쇠 또는 절두체 삭제 | 절두체 안 미관측 | ❌ **무시** | **STVL (현재)** |
| BEV occupancy(학습) | unknown 유지 | 명시적 3-state | 학습 | 자율주행 스택 |

**STVL 만 예외**이고, 그것은 GPU 없이 3D 를 싸게 하려는 타협이다. 절두체 clearing 은
"이 복셀이 시야 원뿔 안이다 → 보였어야 한다 → 포인트가 없다 → 없다" 고 **기하로 추론**하며,
최소 측정거리보다 가깝거나 · 낮은 물체가 하단 화각을 벗어나거나 · 다른 물체에 가려질 때
전부 틀린다. `decay_model: -1` 은 **시간에 의한 삭제만** 막을 뿐 이 경로를 막지 않는다.

우리는 Orin Nano 를 쓰고 있으므로 그 타협을 받아들일 이유가 약하다 — nvblox 이전이
이 지점에서 정당화된다. 다만 **nvblox 로 옮겨도 낮은 물체가 안 보이는 것은 그대로**이고,
ESDF 를 2D 로 뽑을 때 높이 구간 문제로 다시 나타난다. S2 는 어느 쪽으로 가든 먼저 한다.

### 계획 조정 (사용자 승인)

S2 먼저 → STVL 은 S4 3회를 통과할 만큼만 → S5 기준선 → Phase N.
S3(동적 망각)은 STVL 의 구조적 한계이므로 **깊게 파지 않고 한계를 문서화**하고
nvblox 비교 항목으로 넘긴다.
