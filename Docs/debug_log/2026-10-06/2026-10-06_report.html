단계별 회전 실측: rf2o 가 미끄러짐을 실제로 따라가나 §1~§4

10-02 에 찾은 원인은 제자리 회전 중 차체가 미끄러지는데 휠·자이로 EKF 가 그걸 못 본다는 것이었다. 오늘은 rf2o 를 정식 launch(ekf.launch.py rf2o:=true)로 EKF 에 넣고, 비교용 그림자 EKF A(지금 구성)를 함께 띄웠다. 그 상태로 ±90° 를 한 번씩 돌 때마다 사용자가 오른쪽 앞끝과 출발 표시 사이 대각 거리를 줄자로 쟀다. 판정 기준은 주행 전에 ±3 cm 로 정했다.

무엇을 보면 되나

  • 짝수 단계에서 EKF B 오차 0.0 / 0.1 / 0.7 cm. 미끄러짐을 거의 그대로 따라간다.
  • 홀수 단계에서 B 가 −2.3~−2.9 cm 로 일정하게 치우친다. 원인은 확인하지 않았다(직진 축척 0.93 또는 오른쪽 앞끝 위치 오차로 추정).

결론

  • 오프라인 R2 결과(4.3 cm)가 라이브에서도 재현됐고 더 좋았다(1.5 cm).
  • EKF A 가 휠·자이로만으로는 미끄러짐을 못 본다는 10-02 결론을 같은 시각 비교로 다시 확인했다.

게이트 CPU 줄이기 §5, §9

게이트가 자이로를 200 Hz 로 받느라 CPU 를 39 % 썼다. 회전 속도 기준을 EKF 출력 ω(30 Hz, 비교 창 0.15 s)로 바꿨다. EKF 의 ω 는 자이로가 결정하고 rf2o 는 ω 를 넣지 않으므로 순환 의존은 없다. bag 재생에서 정확도 차이는 최대 0.7 cm 였고, 라이브 정지 10 s 측정에서 16 % 였다.

내 실수: 첫 재생 검증의 정리 단계가 pkill -f ekf_node 처럼 이름으로 프로세스를 죽였다. 그래서 라이브 스택의 EKF·rf2o·게이트까지 꺼졌고, 그때 잰 CPU 수치는 무효다. 지금은 재생 launch 의 프로세스 그룹만 PID 로 정리한다.

EKF 는 rf2o 를 얼마나 믿나 (사용자 질의) §6~§8

상황휠 σ (vx · vy)rf2o σ (vx · vy)rf2o 실효 몫 (근사)
직진·정지0.02 · 0.010.10 · 0.03vx ≈ 2 % · vy ≈ 4 %
제자리 회전0.3 · 0.30.03 · 0.03≈ 98 %

근사는 1/σ² × 발행 주기(휠 25 Hz, rf2o 10 Hz)로 계산했고, 과정 잡음은 무시했다. σ 는 지금 두 단계 이산값이다. 그래서 |ω| 경계에서 가중이 뛰고, 휠(0.10)과 rf2o(0.15)의 판정 문턱이 달라 틈이 있다. 연속 σ·품질 σ 는 계획 ⑥에 넣었다. 사용자가 제기한 전선 밟기는 영향 표(라이다 평면 기울어짐, rf2o 가짜 병진, nvblox 유령)와 전선 시험 항목 W 로 정리했다. 계획 순서는 사용자가 확정했다: CPU → 사람 T1·T2 → rf2o 켠 F2 순회 비교 → 피벗 회전 → 전선.

회전 중 가림: bag 에 몸을 그려 넣은 합성 §10~§11

실제 사람이 같은 동작을 반복하기는 어렵다. 그래서 단계별 실측 bag 의 라이다 스캔에 원기둥 모양의 몸을 그려 넣고, rf2o·게이트·EKF 를 새로 띄워 재생했다. 2D 라이다라 몸의 거친 모양은 문제되지 않는다는 데 사용자도 동의했다. 줄자 값이 있으므로 같은 기준(평균 |예측 − 줄자| ≤ 3 cm)으로 판정했다. 방법 확인: 가림 0 % 재생이 라이브 결과(1.5 cm)를 1.6 cm 로 재현했다.

어디서 틀어졌나

  • B 와 진실 대용값의 어긋남은 대부분 회전 중에 쌓였다(경로 1.6~4.2 m). 정지 중에는 G2 가 수천 개를 버려 0.2~0.3 m 로 막았다.
  • G1(자이로 일치)은 C·D 에서 27·19 개만 걸렀다. 회전은 맞고 병진만 틀린 오염이라 G1 이 보지 못한다. §7 에서 예상한 맹점이 측정으로 확인됐다.

한계

  • 진실 대용값은 bag 의 라이브 EKF B 다(줄자 대비 1.5 cm).
  • 합성 몸은 원기둥이고 움직임은 사인파다. 실제 사람의 움직임과 같다는 근거는 없다.
  • 정지한 몸 72 % 가 오히려 좋은 것은 rf2o 가 고정된 몸 자체를 정합 특징으로 쓴 결과로 추정한다.

rf2o 품질 검사: G3 기각, G4 설계 §12~§13

G3 는 직전 스캔을 rf2o 가 추정한 움직임으로 옮겨 이번 스캔과 겹쳐 보고, 5 cm 넘게 어긋난 점의 비율 q 를 재는 방식이다. q 만 기록하는 보정 재생을 먼저 돌려 조건별 분포를 봤다.

G4 는 rf2o_gate.py v_mode / ekf.launch.py gate_v:=on 으로 구현했다(기본 끔). 5 조건 재생 A/B 를 돌리던 중 사용자 요청으로 중단했고 결과는 없다. 부분 결과도 판정에 쓰지 않는다. 예상 비용도 있다: rf2o 를 버리는 순간에는 실제 미끄러짐도 못 본다. 그래서 깨끗한 조건이 나빠지는지가 판정의 핵심이다.

정정·실수 기록 원칙: 지우지 않고 남김

  • 재생 정리 스크립트가 이름 기반 pkill 로 라이브 스택을 죽였다. 그때의 CPU 수치는 무효이고, 지금은 PID·프로세스 그룹으로만 정리한다. 같은 이유로 ssh 명령 안의 pkill 이 자기 자신을 죽인 일도 있었다.
  • q 를 csv 에 쓰는 줄이 편집 중 조용히 빠졌다. 보정 재생 첫 회는 q 가 기록되지 않아 다시 돌렸다.
  • 재생 제한 500 s 가 bag 길이(2021 s)보다 짧아 기록기가 저장 전에 끊겼다. 3000 s 로 늘렸다.
  • T1 때 로버가 출발 테이프에서 다른 방향을 보고 있었다. 지도 위 자세가 틀렸을 수 있으므로 주행 전에 다시 prep 해야 한다.
