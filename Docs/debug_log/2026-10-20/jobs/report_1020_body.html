10-20 cuVSLAM 융합과 공유메모리

프로젝터를 끈 구성에서 cuVSLAM 이 방향을 꾸준히 잘 맞추는 것을 두 번째 주행으로 재현했습니다. 그것을 EKF 에 넣으면 무엇이 좋아지는지 bag 재실행과 실시간 그림자 주행으로 쟀고, 주행 중 cuVSLAM 영상이 빠지는 원인을 UDP 소켓 버퍼로 찾아 카메라와 cuVSLAM 사이를 공유메모리로 바꿨습니다. 깊이 해상도가 상자 번짐에 듣는지도 확인했습니다.

영상이 빠지는 이유와 공유메모리§7 · §9

  • UDP 소켓 수신 버퍼 상한은 208 kB 인데 IR 한 장이 307 kB 입니다. 정지 중에도 초당 39 개 패킷이 버퍼 넘침으로 버려졌습니다.
  • nvblox 가 깊이를 빠짐없이 받는 것은 데시메이션으로 깊이가 160×120, 38 kB 이기 때문입니다(처음에 614 kB 라고 잘못 말했음). 같은 경로에서 크기만 바꾸면 38 kB 는 15.0 Hz, 614 kB 는 13.3~14.1 Hz.
  • 09-09 에 공유메모리를 끈 이유를 다시 보니 '공유메모리 자체가 원인' 은 과한 결론이었고, 확인된 것은 강제 종료와 파일 강제 삭제 문제까지였습니다. 재기동 시험은 정리 없이 강제 종료를 섞어 15/15, 공식 정리 도구로 30/30 정상.
  • 그래서 카메라와 cuVSLAM 두 프로세스만 공유메모리 + UDP 로 바꿨습니다(dds_shm:=true, 기본 끔). 나머지는 UDP 그대로입니다.

공유메모리 전용 시험 설계 결함 §7.3b

하려 한 것§7.3a(SHM+UDP, 30/30 통과)에서 "영상이 정말 공유메모리로 갔다" 는 근거가 UDP 증가량(간접)뿐이라 직접 근거를 만들려 함. 컨테이너 구독자에게만 공유메모리 전용 설정(fastdds_shm_only.xml, UDP 블록만 지움)을 주고 30 주기. 본 것outputs/run_shm_test_shmonly.txt: 컨테이너 구독 30 주기 모두 0.0 / 0.0 Hz, 호스트 구독 15.0 / 15.0, 공유메모리 오류 0, /dev/shm 파일은 양쪽에서 같은 것. 처음 추론"호스트 → 컨테이너 공유메모리가 안 통한다" 로 읽을 뻔함. 그러면 §7.3a 통과는 전부 UDP 였다는 뜻이 되어 계획이 무너짐. 의심한 이유수신 0 인데 오류도 0. 전송 경로 고장이면 세그먼트 · 포트 오류가 남는데 없음. '받을 게 있는데 못 받음' 이 아니라 '상대를 모름'(발견 실패)의 서명. 판별chk_shm_path.sh 두 변형. V1 발행 · 구독 모두 공유메모리 전용 → 컨테이너 150 수신(UDP 가 없으니 공유메모리로 온 것). V2 발행만 SHM+UDP, 구독은 전용 → 같은 호스트의 구독자까지 0. 결론통신 설정 집합이 다른 참가자끼리는 서로를 못 찾는다. 0 Hz 는 시험 설계 탓이고 공유메모리 자체는 통한다. 왜 못 찾는지(발견 트래픽이 어느 경로로 가나)는 미확인. 알아보는 법① 수신 0 + 오류 0 이면 먼저 발견 문제를 의심(ros2 topic info -v 로 상대 엔드포인트가 보이나). ② 경로를 가르는 시험은 한쪽만 바꾸지 말고 모든 참가자를 같은 단일 설정으로. ③ 한쪽만 바꾼 시험은 1 주기 연기 확인에서 Hz 가 나오는지 보고 30 주기로.

측정 노드가 버퍼 카운터를 오염시킨 측정 창 §9.3
