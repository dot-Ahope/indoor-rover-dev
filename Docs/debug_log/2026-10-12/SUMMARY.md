  - 신뢰성 전송 토픽(/tf)은 버려지면 발행자가 다시 보낸다 → 발행자(EKF·위치 추정 등)의 일이 늘고 통신량이 더 늘어난다 → 더 버려진다. 이것이 '포화가 한번 시작되면 끝까지 유지'와 'EKF 가 3 배 무거워짐'의 그럴듯한 설명이다(**추정**).
  - 한계: 위 손실 수치는 **부팅 뒤 누적**이다. 오늘 내가 한 수십 번의 재기동·`ros2` 조회(그때마다 탐색 통신 폭주)도 포함된다. 손실이 큰 소켓 대부분은 탐색용 포트다. → **포화가 시작되는 순간에 손실이 급증하는지는 아직 측정하지 못했다.**
- 그래서 넣은 계측: 주행 래퍼 `job551_f0drive.sh` 가 2 s 마다 커널 누적 손실과 소켓별 손실을 기록한다(`/tmp/net_<이름>.log`. 파일 읽기만 하고 DDS 참여자를 만들지 않는다). 다음 주행에서 포화 시작 시각과 대조한다.
- 고칠 방향(검증 뒤):
  - 수신 버퍼 키우기(`net.core.rmem_max`·`rmem_default`, 예: 8~26 MB — 큰 메시지를 쓰는 ROS 2 의 일반적인 조정. sudo 필요 → 사용자 결정).
  - 궤적 메시지 줄이기(`mppi_viz:=lite`, 28 kB).

### §8.3 사용자 질문: "공유메모리 방식을 다시 사용하는 건 어떤가" — 검토(주행 없음, `jobs/job968_shm.sh` → `outputs/j968_shm.txt`)

- 판단(제안): **지금은 바꾸지 않는다.**
  - ① §8.2 는 아직 추정이다. 원인이 수신 버퍼가 아니면 전송 방식을 바꿔도 안 고쳐지고, 실패 양상만 하나 더 생긴다.

### §8.4 사용자 정정: "DDS 공유메모리가 아니라, **Jetson 보드 고유의 공유메모리**(CPU·GPU 통합 메모리)를 쓰면 더 낫지 않겠나" — 정리(주행·측정 없음, 지식 기반 설명)
- §8.3 은 질문을 DDS 공유메모리 전송으로 잘못 읽고 답했다(내 오독). §8.3 의 내용 자체는 그 주제에 대해 유효하다.
- Jetson 통합 메모리가 하는 일: CPU 와 GPU 가 같은 물리 RAM 을 쓴다 → **한 프로세스 안에서** 영상·복셀 같은 큰 데이터를 CPU↔GPU 로 옮길 때 복사를 없앨 수 있다(CUDA 통합/고정 메모리, Isaac ROS 의 NITROS 가 이를 ROS 노드 사이에 적용).
- 우리 스택에서 해당하는 곳: nvblox 의 GPU 통합, 이후 계획한 cuVSLAM·사람 마스크(JetPack 7.2 이전 Phase). 지금 nvblox 3.2.5 가 깊이 영상을 NITROS 로 받는지 일반 ROS 메시지로 받는지는 **미확인**이다(카메라 노드는 호스트, nvblox 는 컨테이너라 지금은 DDS 를 거친다).
- 오늘의 병목과의 관계: 오늘 문제는 **프로세스 사이 ROS 메시지 전달**(DDS · UDP 수신 버퍼, §8.2 추정)이다. 통합 메모리는 프로세스 '안'의 CPU↔GPU 복사를 줄이는 것이라 이 병목에는 직접 닿지 않는다.
- 같은 취지(복사 없이 넘기기)를 프로세스 사이 전달에 적용하는 수단:
  - **노드 합치기(composition)**: Nav2 서버들을 한 프로세스(컴포넌트 컨테이너)에 올리면 그 사이 메시지(코스트맵·경로·TF 등)가 DDS 를 거치지 않고 포인터로 넘어간다. Nav2 가 자원이 적은 보드에 권하는 방식(`use_composition`). bag 기록기로 가는 것은 여전히 DDS.
  - DDS 공유메모리·대여 메시지(§8.3).
- 제안:
  - 단기는 그대로: 계측 재현 → 수신 버퍼.
  - 중기 후보로 'Nav2 합치기'를 기록한다(부하·통신량을 구조적으로 줄임. 검증 필요).
  - 통합 메모리·NITROS 는 로드맵의 JetPack 7.2 이전 Phase 에서 다룬다.

### §8.5 사용자 제안: "DDS 공유메모리 제로카피를 쓴다면, 영상·라이다 같은 대용량은 제로카피로, 문제가 생기는 부분은 UDP 로 나누면 어떤가" — 검토(주행·측정 없음, 지식 기반 + 오늘 확인한 사실)
- 가능한 단위:
  - Fast DDS 의 전송 수단은 **토픽별이 아니라 프로세스(참여자)별**로 정해진다. 두 프로세스가 모두 공유메모리를 켜고 같은 호스트에 있으면 공유메모리로, 한쪽이라도 UDP 전용이면 UDP 로 통신한다.
  - → '토픽을 골라' 나눌 수는 없지만 **'프로세스를 골라' 나누는 것은 가능**하다. 제안의 취지는 이 단위로 구현된다.
- '제로카피'의 한계(Humble):
  - 복사가 아예 없는 전달(대여 메시지)은 **크기가 고정된 단순 메시지**에서만 된다. `sensor_msgs/Image`·`PointCloud2`·`LaserScan` 은 가변 길이 배열이라 해당하지 않는다.
  - 이들에 공유메모리 전송을 쓰면 '복사 0'은 아니지만 **UDP 경로(커널 소켓 버퍼·64 kB 조각내기)를 통째로 건너뛴다**.
  - 진짜 제로카피가 필요하면 같은 프로세스에 합치기(§8.4) 또는 NITROS 다.
- 우리 스택에 대입:
  - 대용량 흐름 = 깊이 영상(호스트 realsense → 컨테이너 nvblox, 약 614 kB × 15 Hz ≈ 9 MB/s · 계산값) · 카메라 점군 · 코스트맵 · MPPI 궤적(206 kB × 10 Hz). 라이다 스캔은 작다(수십 kB).
  - nvblox 컨테이너는 이미 공유메모리 가능 상태(§8.3: `ipc host`, 프로파일 없음). **realsense 노드(와 depth_relay)만 공유메모리를 켜면** 깊이 영상이 UDP 를 떠난다.
  - 09-09 에 조용히 죽었던 것은 ekf_node·slam_toolbox 였다. 재기동이 잦은 것은 Nav2 다 → 이들은 UDP 로 둔다(제안의 '문제 생기는 부분은 UDP').
  - 카메라 → nvblox 경로는 주행 게이트 J(nvblox 깊이 ≥ 10 Hz)가 이미 감시한다 → 공유메모리 고아 문제로 끊겨도 '조용한 실패'가 아니라 게이트에서 잡힌다.
- 주의·미확인:
  - 오늘 포화의 원인이 UDP 수신 버퍼라는 것은 아직 추정이다(§8.2). 깊이 영상 9 MB/s 가 이미 같은 UDP 로 문제없이 15 Hz 로 들어가는 점은 '크기만의 문제'가 아닐 수 있음을 뜻한다.
  - sensors.launch 는 prep 마다 재기동된다 → 공유메모리 고아가 생기는 조건이다. prep 시작에 `fastdds shm clean` 이 필요하다.
  - 프로세스별 프로파일 지정(노드별 환경 변수)과 컨테이너 상호 동작은 실제로 해 봐야 안다.
- 판단: **구조로서는 타당하다(프로세스 단위 혼합).** 다만 오늘 문제의 해결책으로 바로 넣기보다, 원인 확정(계측 재현) 뒤 '카메라 → nvblox 만 공유메모리'를 별도 A/B 로 시험하는 것을 제안한다(판정: 게이트 J · 깊이 주기 · 전체 UDP 손실·CPU 변화).

### §8.6 사용자 의견·질문: "DDS 로 공유메모리 통신이 되면 하는 게 맞다고 본다. micro-ROS 때문에 문제가 생기나?" — 답(주행 없음)

  - ② 안전장치:
    - prep 시작에 `fastdds shm clean`(고아 정리).
    - 기동 로그에 `Failed init_port`·`RTPS_TRANSPORT_SHM Error` 가 있으면 prep 불합격.
    - '발행자 존재' 확인(odom→base TF · /map · /scan · 깊이).
  - ③ 정지 시험(주행 없음): 혼합 프로파일로 prep → 게이트·그래프·정지 부하·UDP 손실 비교. Nav2 재시작 5 회 반복에 고아가 재발하는지 확인.
  - ④ 통과하면 주행 A/B(15 + 궤적 발행 원래대로): 포화가 사라지는지 본다.
