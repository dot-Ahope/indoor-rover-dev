| >0 | 0 | 마킹 자체 실패 (높이·문턱·사거리 문제) |
전역경로·컨트롤러 영향을 배제하므로 코스트맵 거동만 순수하게 본다.

## ⚠⚠ 정정 2건 — 코스트맵은 정상이었다 (`job74`, `job75`)

### 정정 B: 소프트웨어 기억은 **양쪽 코스트맵 모두에서 작동**
`job75`(프레임 정정판, 전방 축을 매 주기 재계산해 드리프트 무관, 40cm 저속 접근):

| +0.23m | 0.30 (100) | 0.46 (99) | 492 |

### 그래서 남은 용의자는 **컨트롤러(RPP)**
코스트맵 정상 + 플래너가 좌 +0.38m 우회 경로 생성 → 그런데도 job70 은 최대 좌편향 0.022m 로 직진했다. 후보:
1. **RPP 코너컷**: `use_velocity_scaled_lookahead_dist true` 에서 lookahead = v×`lookahead_time` = 0.08×2.0 = 0.16m → 하한 `min_lookahead_dist 0.35` 로 클램프되어 **항상 0.35m**. 우회폭 0.38m·길이 ~0.5m 의 급한 곡선을 0.35m 전방 점만 보고 따라가면 크게 잘라먹는다. 오늘 진동 억제로 min 0.20→0.35 로 올린 것이 회피에는 역효과.
2. **충돌검사 지평이 너무 짧다**: `max_allowed_time_to_collision_up_to_carrot 1.5s` × 0.08m/s = **0.12m** 앞만 검사. 상자를 12cm 앞에서야 인지하므로 회피가 아니라 정지에도 늦다.
- 다음: ① 충돌검사 지평 상향(1.5→5.0s = 0.4m) ② `min_lookahead_dist` 0.35→0.25 로 낮춰 추종 강화 후 재주행. ①은 안전상 무조건 이득, ②는 진동과의 트레이드오프이므로 지표(§5.y)로 재확인.

## ★ 진짜 원인 확정 `job76` — **충돌검사 지평이 0.12m 였다**
조치: `max_allowed_time_to_collision_up_to_carrot` 1.5 → 5.0s, `min_lookahead_dist` 0.35→0.25 (임시).
- 경로 질의: 우측 −0.37m 우회, 61점 1.76m, **최대 비용 99**(내접 스침).
- 주행 `job76` 궤적: t=0.9~3.6s **ω −0.22 로 우회전하며 실제로 우측 우회 시작**(yaw −18°) → t=3.6s 정지
  → 복구 후 재시도 → t=7.2s 정지 → **BackUp 복구 4.1s** → 재전진 → stuck_monitor 취소(비율 0.23).
- 컨트롤러 로그: `[follow_path] Aborting handle` 반복, `behavior_server: Running backup / backup completed`.
- **즉 이번엔 밀고 지나가지 않았다.** RPP 가 충돌을 감지해 스스로 멈추고 후진 복구를 했다.

### 결론
`max_allowed_time_to_collision_up_to_carrot` × 현재속도 = 실제 충돌검사 거리.
0.08 m/s 에서 1.5s = **0.12m** 뿐이라, 코스트맵이 상자를 정확히 알고 플래너가 우회 경로를 내도
컨트롤러는 12cm 앞만 보고 그대로 밟고 지나갔다. job61·66·70 의 "피하다가 직진" 이 전부 이것이다.
(코스트맵 소거설·전역 미마킹설은 모두 내 오진이었고 `job74/75` 로 반증됨.)
- 5.0s → 0.40m 검사. **밀고 가는 현상 소멸**을 job76 으로 확인.
- 남은 한계: 이 통로에서 우측 슬롯은 상자와 우벽 사이 여유가 사실상 0(경로 최대 비용 99 = 내접 스침)이라
  검사가 정상 작동하면 abort→복구 루프가 된다. **통로 여유 확보가 근본 해법**이며, 이는 센서·제어가 아니라 배치 문제.

### 반영
- `max_allowed_time_to_collision_up_to_carrot: 5.0` 파일 반영·배포(안전상 무조건 이득).
- `min_lookahead_dist`/`lookahead_dist` 는 오늘 §5.y 로 검증된 **0.35/0.40 으로 원복**(0.25/0.30 은 이번 주행이 복구 루프로 오염돼 깨끗한 비교가 안 됨).

## ⚠ 소프트웨어 기억의 부작용 — 전역 코스트맵 유령 장애물 누적 (`job77`, `job79`)
사용자 중단 요청("멈춰라 이상하게 움직인다") — 정당한 판단이었다.
- `job77`(상자를 한쪽에 여유 두고 재배치, 우측 65cm 확보): 경로 질의가 **직선 1.40m 에 경로 5.79m(비 4.14)**, 우측 −1.11m 까지 우회. 주행은 82.3s 동안 1.31m 만 이동하고 **ABORTED**, 최종 오차 133cm.
- `job79`(전역 코스트맵 ASCII): 로버 주변이 X/# 로 가득 찼다. 통로 전체가 막힌 것처럼 보이니 플래너가 몇 안 되는 빈칸을 누비는 기괴한 경로를 낸 것.
- **원인: `raytrace_min_range 0.90` 을 전역에도 걸었기 때문.** 전역 코스트맵은 롤링이 아니라 **누적**이라, 근접 소거를 막으면 로버가 지나간 자리마다 마킹이 영구히 남는다. 오늘 여러 번 주행하며 그것이 쌓였다.
- 로컬은 3×3m 롤링이라 지나가면 자동 소멸하므로 같은 설정이 안전하다.

### 최종 설정 (기억은 로컬 전용)
| 항목 | 로컬 | 전역 | 근거 |
|---|---|---|---|
| depth `raytrace_min_range` | **0.90** | **0.30** | 로컬=롤링(자가 치유) / 전역=누적(유령 축적) |
| `max_allowed_time_to_collision_up_to_carrot` | 5.0s (=0.40m) | — | 밀고가기 방지 (job76 검증) |
- 전역이 근접에서 상자를 잃어도, **로컬 기억 + RPP 충돌검사 0.40m** 가 밀고 가는 것을 막는다(job76 에서 abort·BackUp 확인).
- 적용·배포·양 코스트맵 초기화 완료. 파라미터 조회로 로컬 0.9 / 전역 0.3 확인.

## 오늘 얻은 것 / 남은 것
**확정된 인과**
1. 밀고 지나간 진짜 원인 = RPP 충돌검사 지평 0.12m(1.5s×0.08m/s). 5.0s 로 해소.
2. 깊이 코스트맵·소프트웨어 기억은 정상 동작(job74/75 로 프레임 정정 후 확인).
3. 기억을 전역에 걸면 유령 누적 → 로컬 전용이 정답(job79).
4. stuck_monitor 는 오탐 0, 정탐 3/3 + 실주행 복구루프 2회 정확 감지.

**내가 냈던 오진(기록 보존)**
- "근접 소거로 상자가 지워진다" → 지워지지 않았다(job75).
- "전역에 depth 가 마킹되지 않는다" → 프레임을 섞은 내 조회 오류(job74).
- "통로가 상자 폭 0.30m 로 막혔다" → min/max 오독, 실제 0.18m.

**다음 세션**
1. 배터리 충전(11.99V 로 종료). 재개 시 스택 기동 → 보드 RESET 필요 여부 확인.
2. 깨끗한 회피 1회: 상자 한쪽 0.6m 이상 여유 + 전역 코스트맵 초기화 후 즉시 주행(누적 전에).
3. 성공하면 N2 전체 지도 작성 → N3 프론티어 탐사.
4. 미해결: 전역 코스트맵 누적 일반 대책(주기적 초기화 or rolling global), RPP 코너컷 정량화.

## 검토: 동적 장애물 vs 근접 기억의 충돌 (사용자 질문)
**질문**: 전역에 장애물을 남기면, 실제로 치워진 물체가 코스트맵에 유령으로 남지 않는가? 해법은? 현재 문제와 충돌하는가?

### 충돌은 실재한다
- 근접 사각 대응은 **기억**(못 보는 것을 지우지 말라)을 요구하고, 동적 환경은 **망각**(없어진 것을 지워라)을 요구한다. 정면으로 반대다.
- 오늘 job79 가 그 충돌의 실물: 기억을 전역에 걸었더니 지나간 자리마다 유령이 쌓여 1.4m 목표에 5.79m 경로가 나왔다.

### 해소 원리: '지우지 않을 반경' 을 **물리적 사각과 일치**시킨다
Nav2 의 `raytrace_min_range` 는 "이 반경 안에서는 소거하지 않는다" 이다. 그러므로
- 이 값이 **센서 최소 측정거리와 같으면**: 못 보는 곳만 안 지우고, **볼 수 있는 곳은 전부 정상 소거** → 치운 물체는 잊는다. 충돌이 사라진다.
- 이 값이 그보다 **크면**: 볼 수 있는데도 안 지우는 영역이 생겨 유령이 쌓인다. 0.90 이 바로 이 경우였다.

실측(job71 접근 로그): 카메라~물체 0.25m 에서 깊이점 288개 → 0.21m 에서 8개. **최소 측정거리 ≈ 0.22~0.25m.**
→ **로컬 `raytrace_min_range` 0.90 → 0.35 로 정정**(사각 0.25 + 여유 0.10). 전역 0.30 은 이미 같은 정책이라 유지.

### 남는 한계와 업계 관행
- 반경 0.35m 이내의 유령은 원리상 못 지운다(정보가 없으므로). 로컬은 3×3m 롤링이라 로버가 지나가면 소멸하고, 전역은 0.30 으로 최소화.
- 더 정교한 해법은 **확률적 3D 점유 지도**(OctoMap 류): 셀마다 점유 확률을 갖고 관측이 없으면 확률을 유지, 나중에 자유공간으로 관측되면 낮춘다. 기억과 망각이 자연스럽게 공존한다. 다만 CPU 비용이 크고 Nav2 기본 스택 밖이다.
- 실무 관행은 ① 롤링 창으로 누적을 물리적으로 상한 ② 재계획 실패 시 코스트맵 초기화(Nav2 BT 의 ClearCostmap 복구) ③ 정적 구조는 SLAM 지도, 일시 장애물은 짧은 기억의 센서 레이어로 분리.
- 사람처럼 계속 움직이는 물체는 0.35m 기억이 문제되지 않는다(끊임없이 재관측되므로).

### 결론
현재 구성과 **충돌하지 않는다**. 오히려 0.35 로 낮추는 것이 근접 사각 보호를 유지하면서 동적 장애물 망각을 회복하는 정답이다. 다음 세션 첫 주행에서 ① 회피 성공 ② 상자를 치운 뒤 코스트맵에서 사라지는지 두 가지를 함께 확인한다.

## ★★ 상자 소실의 진짜 기전 — 거리에 따라 보이는 면이 바뀌어 복셀 수가 줄고, `mark_threshold` 가 걸러냄
**사용자 Foxglove 직접 관측(job81)**: "상자가 인식될 때는 피해가는 경로를 따라가다가, 상자가 사라지니 바로 상자가 있는 곳으로 경로를 수정하여 그쪽으로 이동." → 코스트맵에서 상자가 실제로 사라진다는 결정적 증거.

### 기전 (기하)
카메라 z=0.143, 상자 높이 0.11m.
| 카메라~상자 | 보이는 면 | 깊이점 z 분포 | 복셀 칸 수 |
|---|---|---|---|
| 1.0 m | 앞면 0.00~0.11 | 넓음 | 3칸 |
| 0.7 m | 앞면 | 넓음 | 3칸 |
| **0.5 m 이하** | **윗면(z≈0.11) 위주** | **0.11 부근으로 수축** | **1칸** |
- 가까워질수록 카메라가 상자를 **내려다보게** 되어 앞면 대신 윗면이 보인다. 윗면은 z가 0.11 하나로 몰리므로 복셀이 `[0.10,0.15)` 한 칸뿐.
- 여기에 오늘 오전 내가 올린 `mark_threshold: 1`(= 복셀 2개 이상이어야 점유)이 걸려 **마킹이 사라진다.**
- `min_obstacle_height 0.08` 도 악화 요인: 쓰이는 높이대가 0.08~0.11 의 3cm 뿐이라 애초에 복셀 여유가 없었다.
- 앞선 `raytrace_min_range` 는 무관했다. 소거가 아니라 **마킹이 조건 미달로 끊긴 것**.

### 조치 (local·global 동시)
| 항목 | 구 | 신 | 근거 |
|---|---|---|---|
| `mark_threshold` | 1 | **0** | 복셀 1개만 있어도 마킹. 윗면만 보이는 근접 구간을 살림 |
| depth `min_obstacle_height` | 0.08 | **0.06** | 앞면(0.045~0.101)을 더 포함해 복셀 확보. 바닥 실측 z≈−0.02 대비 여유 8cm |
- 잡음 억제는 `min_obstacle_height`(바닥 배제) + `obstacle_max_range 1.2`(원거리 잡음)가 담당. `mark_threshold` 로 잡던 것을 이 둘로 옮긴 셈.
- 배포·런타임 적용·코스트맵 초기화 완료(로컬/전역 모두 mark_threshold 0, min_h 0.06 확인).
