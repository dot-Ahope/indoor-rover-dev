## 판단
- **기동 임계 ≈ 0.012~0.016 m/s(휠속도)**. 0.012는 "되다 말다"(정지마찰 경계) — 승격된 값 자체가 데드밴드 안이었음.
- 0.016·0.020 모두 신뢰 가능하나 임계가 전압·바닥·트랙장력에 따라 움직이므로 **마진 있는 0.020 채택**. 승격 구간에선 지령 크기 무관 동일 속도라 0.016의 분해능 이득은 실질적으로 없음.
- **플래시 전 데드락 지점(ω=0.05) 해소 확정** — 이제 Nav2 컨트롤러의 미세 명령이 실행됨.

### 메커니즘 (설계 충돌)
- `safety_monitor.c`: 지령 ≥ `V_TARGET_THRESH 0.015 m/s` 인 휠이 600ms 창에서 3mm 미만 이동 → STALL → `s_fault` **latch** (CLI 'c' 또는 리셋 전까지 지령 차단).
- 데드밴드 승격값 `MIN_WHEEL_SPEED_MPS 0.020` 은 이 임계 바로 위 → **부하 상태**(한쪽 휠 역회전 선회, 근접 기동)에서 승격된 휠이 정지마찰을 못 이기면 → 정확히 STALL 조건 충족 → 로버 전체 잠김.
- 무부하 데드밴드 테스트(제자리 회전)에선 안 걸렸으나, **Nav2 실주행의 부하 조건에서 재현**. 승격이 "명령은 나가지만 안 움직이는" 상태를 만들고 스톨 감지가 그걸 구속으로 오판.
- **fault 해제 경로가 UART5 CLI 'c' 뿐, ROS 경유 없음** → 자율주행 중 발생 시 Nav2 가 회복 불가. 자율운용과 양립 불가한 정책.

### 조치·계획
- 즉시: 보드 RESET(사용자) → 세션 재수립 → 로버 복도 중앙 재배치 → RPP A/B 실행.
- 준비 완료(빌드됨): 컨트롤러 RPP 전환, **Spin 제거 커스텀 BT**(`config/nav_to_pose_no_spin.xml`, BackUp 0.15m/0.05m/s 우선) — 벽 근접 실패 시 spin 이 접촉을 유발한 2건 근거.
- 다음 펌웨어 묶음에 추가 (§6 항목과 통합):
  1. **스톨 감지 하한을 승격값 위로**: `V_TARGET_THRESH` > `MIN_WHEEL_SPEED_MPS` (예 0.025) — 승격 구간 명령은 "best effort" 로 취급, 그 이상만 구속 판정.
  2. **fault 비래치화 또는 자동 해제**: 정지 지령(0,0) 수신 시/쿨다운 후 자동 clear. 또는 ROS 서비스 `/rover/clear_fault` 노출.
  3. (기존) 기동 보조(적응형) — 승격 자체를 "킥 후 복귀" 로 바꾸면 이 충돌의 근본 원인(승격된 저속 명령 지속)이 사라짐.
