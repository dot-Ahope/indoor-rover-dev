# 2026-10-08 — 전역 카메라 기억: nvblox 로 풀 수 있나 (STVL 정리 검토)

전날 기록: `Docs/debug_log/2026-10-07/SUMMARY.md` §8(전역 카메라 STVL 시험: C1 통과·C2 불합격), §10(계획기·MPPI 지도 불일치), §16(STVL 제거 검토 질의).

## §1 nvblox 슬라이스로 C1·C2 확인 — 선언(사용자: 다음 단계 진행)
- 배경: 기본 구성엔 STVL 이 이미 없음(로컬 nvblox + 라이다, 전역 정적 + 라이다·카메라 점군 obstacle). 쟁점은 전역 카메라 기억(사용자 조건: 화각 밖은 기억, 카메라가 볼 때는 갱신)을 STVL 대신 이미 도는 nvblox 로 풀 수 있는가.
- 자료: 10-07 상자 시험 녹화 `bags/bag_box1.tgz`(카메라 점군·nvblox 슬라이스 `/nvblox_node/static_map_slice`·TF 포함). 로버 안 움직임(재생·분석만).
- 방법(`jobs/job933_nvslice.py`): 2 s 마다 상자 ② 자리(map x 1.05~1.35 · y −0.30~+0.10, 칸 중심 48 개)를 슬라이스 좌표(odom)로 옮겨 거리 ≤ 0.05 m 인 칸 수.
- 판정(어제 STVL 과 같은 기준):
  - C1 기억: 0.35 m 앞까지 다가간 30 s 동안 상자 칸 ≥ 정지 기준값의 50 %.
  - C2 갱신: 치운 뒤(카메라 점 100 → 0, 14:10:16 무렵) 5 s 안에 0.
  - 참고: 감쇠(0.99·5 Hz ≈ 81 s)로 지워졌다면 '본 것' 이 아니라 '시간' 으로 지운 것 — 치운 순간과 사라진 순간의 간격으로 가른다.
- Jetson 무응답(172.30.1.8·192.168.0.101 ping 0) → PC 에서 분석: `rosbags` 로 bag 을 읽고 nvblox_msgs/DistanceMapSlice 정의(header·resolution·width·height·origin·unknown_value·data)를 직접 등록. 검증: 모든 슬라이스에서 data 길이 = width×height(불일치 0). `jobs/nvslice_pc.py` → `outputs/nvslice_box1.txt`.

### §1.1 결과 — nvblox 는 **치운 뒤 2~3 s 에 대부분 지움(STVL 은 1 분 30 s 넘게 못 지움)**, 가까이서도 유지. 다만 1~2 칸이 64 s 남음
| 구간(10-07) | 상자 ② 자리 nvblox 장애물 칸(48 점 중) | STVL 전역(어제 §8.5) |
|---|---|---|
| 출발 자리 정지 | 9 | 25 |
| 0.35 m 앞까지 접근·30 s(14:00:47~14:01:40) | **17~21** | 25 |
| 후진 뒤 정지 | 14~15 → 14:03:06 부터 8(로버 정지 중 줄어듦 — 가까이서만 본 윗면이 감쇠로 빠진 것으로 추정) | 22~25 |
| 치움 14:10:16(카메라 점 100 → 0) | 14:10:17 12(사람 몸) → **14:10:19 3 → 14:10:21 2** → 14:10:35 1 → **14:11:20 0** | 24 그대로 |
- C1 기억: **통과**(가까이서 17~21 ≥ 기준 9 의 50 %). 단 30 s 유지는 감쇠 수명(≈ 81 s) 안이라 '오래 기억' 의 근거는 아님.
- C2 갱신: 선언 기준(5 s 안에 0)으로는 **불합격** — 8 칸 중 6 칸(75 %)은 3 s 안에 지워졌지만 1~2 칸이 64 s 남음. 남은 칸이 '본 것' 으로 지워졌는지 감쇠로 지워졌는지는 이 자료로 못 가름(감쇠 81 s 와 비슷한 시간).
- STVL 과의 차이(측정): STVL 은 치운 뒤 0 칸도 못 지웠고 nvblox 는 대부분 즉시 지움 → '카메라가 볼 때 갱신' 은 nvblox 쪽이 실제로 동작.
- 한계: nvblox 기억은 감쇠(≈ 81 s)·반경 3 m 밖 삭제로 짧음 → '화각 밖에서 오래 기억' 은 못 함. 전역에 nvblox 층을 다시 넣으면 10-01 §8.24 의 유령 칸(통로 입구 93 칸) 문제가 돌아올 수 있음.
- 다음 후보(오프라인, 로버 안 움직임): f2c2·f2d2 순회 bag 의 nvblox 슬라이스로 '전역에 nvblox 를 넣었다면' 통로 유령 칸이 얼마나 생기는지 + 상자 ② 를 계획기가 제때 알았을지 재계산.

## §2 '전역에 nvblox 를 넣었다면' 재계산 — 선언(사용자: 진행, Jetson 192.168.0.101 복귀)
- 자료: 10-07 순회 bag f2c2·f2d2(nvblox 슬라이스·라이다·/map·TF·/plan). PC 에서 rosbags 로(로버 안 움직임).
- 계산 ①(유령 후보): 1 s 마다 nvblox 슬라이스의 장애물 칸(거리 ≤ 0.05 m)을 map 으로 옮겨, (a) 저장 지도에서 벽(점유)으로부터 0.15 m 넘게 떨어진 빈 곳이고 (b) 같은 시각 라이다 점에서 0.10 m 넘게 떨어진 칸 = '카메라만 본 장애물'(낮은 실제 물체 또는 유령). 위치별로 묶어 지속 시간·크기를 나열 → 실제 물체인지 사용자 확인.
- 계산 ②(상자 ② 를 계획기가 알았을 시점): 복귀 목표에서 nvblox 가 상자 ② 자리를 처음 표시한 시각 vs 경로 계획·재계획 시각.
- 판단 규칙(분석 전): 카메라만 본 칸 묶음 중 실제 물체가 아닌 것이 통로(벽 사이 1.0 m 이하) 안에 10 s 넘게 남으면 '전역 nvblox 는 유령 위험 그대로' → 채택 보류. 없으면 전역 nvblox 층 A/B 주행 후보.

### §2.1 결과 — 카메라만 본 장애물이 통로 곳곳에 **많이** 있음(f2c2 묶음 35·f2d2 41, 지속 10 s 넘는 것 대부분). 실제 물체인지 사용자 확인 필요
- `jobs/nv_global_whatif.py`(첫 판은 주행 중 다시 발행된 /map 을 슬라이스로 잘못 읽어 f2d2 에서 멈춤 — 고침), `outputs/whatif_f2c2_f2d2.txt`, 그림 `Docs/04_navigation/figures/2026-10-08_nvblox_global_whatif.png`(`jobs/render_whatif.py`, 번호 = 칸 수 × 지속 큰 순 15 개).
- 큰 묶음(예): f2c2 남쪽 통로 (−0.09, −4.79) 122 칸·198 s, (−0.37, −1.03) 50 칸·261 s, (2.21, −4.68) 84 칸·91 s · f2d2 (6.17, −2.64) 54 칸·61 s, 상자 ① 근처 (1.29, −0.24) 37 칸·81 s. 거의 모두 저장 지도 기준 통로(벽까지 ≤ 0.5 m) 안.
- 해석(추정):
  - 이 칸들은 **이미 로컬 코스트맵(nvblox 층)에 들어가 MPPI 가 피하고 있던 것** — 로버는 이 상태로 순회를 했다. 전역에 넣으면 계획기가 MPPI 와 같은 것을 보게 되어 §10(10-07) 의 불일치는 줄어듦.
  - 위험: 전역 inflation(0.70 m)은 로컬(0.40 m)보다 넓어 같은 칸이 통로를 더 쉽게 '닫힌' 것으로 만듦 — 10-01 §8.24 의 '통로 입구 유령 93 칸이 통로 셋을 닫음' 과 같은 기제.
  - 상당수는 실제 낮은 물체(의자 다리·바퀴 받침, 바닥 가방·상자, 전선)일 가능성. 저장 지도(라이다 높이)엔 안 보이므로 이 계산만으로는 유령과 못 가름.
- 상자 ② 첫 표시(복귀 구간): f2c2 11:14:22·f2d2 13:17:33 — 둘 다 그 목표의 첫 경로(11:13:27·13:16:44) **뒤**. nvblox 반경 3 m·카메라 1.4 m 한계라 목표 시작 때 계획기가 알 방법은 원래 없음 → 전역 nvblox 만으로는 부족, **보이는 순간 재계획**(주기 재계획)이 함께 필요.
### §2.2 사용자 확인: "대부분 실제 물체였다. f2d2 (0.1, −5.8) 근처는 바닥의 에어캡 — 꽤 투명한 물체도 인식하고 피해 갔다"
- 정정(내 설명): 전역 inflation 0.70 m 은 내접(0.175) 밖에선 '비싼 길' 비용일 뿐 통로를 닫지 않는다 — 10-01 §8.24 의 통로 닫힘은 유령 칸(치명) 자체 때문. inflation 은 그대로 둔다.

## §3 전역 nvblox + 주기 재계획 A/B 주행 — 선언(주행 전)
- B 구성(`navigation.launch.py` 새 인자): `global_camera:=nvblox`(전역 plugins static · nvblox_layer · obstacle(**라이다만**) · inflation) + `replan_hz:=0.5`(BT RateController 0.01 → 0.5 Hz 사본 /tmp/nav_to_pose_active.xml) + `mppi_viz:=true`(순회 기록). rf2o·G4 잔차·그림자 A 그대로. prep `jobs/job934_prep.sh`.
- 0.5 Hz 근거: MPPI 지평 3.2 s 안에 새 경로가 들어오게, 1 Hz(10-01 이전)보다 경로 흔들림 위험을 줄이는 중간값(추정 — 판정 항목으로 확인).
- 코스: f2d 와 같은 10 목표, 남서 두 번 모두 '위치만(f)'(`run_f2c.sh … fullf`), 상자 ①·② 제자리, 사람 없음. A(대조) = 10-07 f2d1·f2d2(남서 정체 1·상자 ② 앞 정지 1).
- 판정:
  - ③-a 10 목표 성공(남서는 SUCCEEDED_XY), 접촉 0(상자 포함), nav_guard 취소 0.
  - ③-b 상자 ②: nvblox 가 처음 표시한 뒤 ≤ 3 s 안에 새 경로가 그 칸을 피함(경로 ↔ 상자 칸 ≥ 0.10 m).
  - ③-c 경로 흔들림: 재계획 사이 경로가 옆으로 0.3 m 넘게 바뀐 횟수 — 목표당 > 5 면 '흔들림 위험' 기록(불합격 아님, 다음 조정 근거).
  - ③-d 부하: 계획기·전역 코스트맵 CPU(재계획 0.5 Hz 비용) 기록.
