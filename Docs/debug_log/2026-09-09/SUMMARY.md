# 2026-09-09 — micro-ROS 링크에서 /wheel_odom 이 사라진 문제

## 0. 이 날의 결론

`/wheel_odom`(732 B) 이 수십 초씩 통째로 사라져 EKF 가 8.5 m 발산하고 Nav2 가 ABORTED 되었다.
**baudrate 를 2,000,000 → 460,800 으로 낮추자 70 s 연속 100% 전달·드롭 0 으로 해소**되었다.

⚠ **이것은 우회이지 근본 해결이 아니다.** 같은 2 Mbps 설정으로 2026-08-27 에는
`/wheel_odom` 49.995 Hz + `/imu/data_raw` 49.999 Hz(≈60 kB/s)가 안정적으로 나왔다.
즉 용량 한계가 아니라 **08-27 이후 생긴 회귀**이며 원인은 아직 미확정이다.

> 이 문서는 하루 동안 세운 가설을 순서대로 남긴다. §6 의 'USB 32 B 엔드포인트가 상한' 결론은
> **틀렸고** §10 에서 반증·정정한다. 틀린 추론을 지우지 않고 남기는 이유는, 어떤 근거로
> 잘못 확신했는지가 결과만큼 중요하기 때문이다.

## 2. 무주행 경로 질의 — 설정 변경 자체는 의도대로 동작 (job91)

장면: 상자가 정면 1.00 m, base_link 기준 y −0.10~+0.20, z 중앙 0.08. 라이다는 상자를 못 보고 정면 243 cm,
좌30° 127 cm / 우30° 78 cm (왼쪽이 넓음).

`job91_query.py 1.80` (Nav2 `compute_path_to_pose` 직접 질의, 주행 없음):

```
경로 길이 2.75m / 직선 1.80m (+52.9%)
최대 횡변위 +0.488m (좌) @ 전방 0.63m
x=0.99m(상자 위치) → y=+0.410m
경로 비용 최대 71 (OccupancyGrid 0~100 스케일)
```

**비용 71 의 해석**: Nav2 `Costmap2DPublisher` 는 내부 0~255 비용을 0~100 으로 축약해 발행한다
(`v = 1 + 97*(i-1)/251`). 역산하면 i ≈ 182. 인플레이션 비용 모델
`cost = 252·exp(−cost_scaling·(d − r_inscribed))` 에 global 값(scaling 3.0, r_inscribed = 반폭 0.165 + 패딩 0.02 = 0.185)
을 넣으면

```
d = 0.185 + ln(252/182)/3.0 = 0.185 + 0.109 = 0.294 m
```

즉 경로의 최근접 장애물 거리 0.294 m, **패딩 포함 차체 외곽에서 10.9 cm 여유**. 상자 왼쪽 끝(+0.20)과
경로 중심(+0.41) 사이 21 cm 와도 일치한다. 09-08 job89 에서 경로가 상자에 붙어 접촉했던 것과 대비되는,
의도한 거동이다.

> ⚠ 단, 이건 **플래너의 계획**이다. 실제 접촉 여부는 컨트롤러(RPP)가 그 경로를 얼마나 따라가느냐에 달렸고,
> 그 주행 검증은 아래의 링크 장애 때문에 **오늘도 완료하지 못했다.**

## 6. [정정됨 — §10 참조] 당시 세운 결론: 병목은 UART 가 아니라 USB (job106, job107)

```
/dev/rover → ttyCH341USB0        (CH340, 1a86:7523)   ← 보드
/dev/rplidar → ttyUSB0           (CP2102N, 10c4:ea60) ← 라이다 (드라이버 cp210x)
agent Cmd: serial --dev /dev/rover -b 2000000

USB 장치 /sys/bus/usb/devices/1-2.1/   speed = 12 Mbps  (Full Speed)
  ep_02 : wMaxPacketSize = 0x20 (32 B), type Bulk    ← OUT
  ep_82 : wMaxPacketSize = 0x20 (32 B), type Bulk    ← IN
  ep_81 : wMaxPacketSize = 0x08,        type Interrupt, interval 1ms
```

당시 나는 이렇게 계산했다: USB Full-Speed 벌크는 1 ms 프레임 단위이고 엔드포인트가 32 B 이므로
실효 상한 약 32~40 kB/s. 관측 최대치(odom 단독 50.9 Hz × 720 B = 36.6 kB/s)와 맞아떨어져 확신했다.

**이 결론은 틀렸다.** 08-27 실측 60 kB/s 가 반증한다(§10). 36.6 kB/s 는 상한이 아니라
그 시점의 우연한 값이었고, 나는 '맞아떨어지는 숫자' 하나로 인과를 단정했다.

`2,000,000 bps` 는 **UART 구간의 선로 속도**일 뿐이고 200 kB/s 의 여유는 쓸 수 없다.
나는 그동안 이 여유가 있다고 잘못 알고 있었다.

### 대역 수지

메시지 크기는 CDR 직렬화 기준. `nav_msgs/Odometry` 는 pose 7 double(56) + 공분산 36 double(288)
+ twist 6 double(48) + 공분산 36 double(288) = 680 B + 헤더/프레임 문자열 ≈ 720 B.
**공분산 576 B 가 전체의 80%** 인데 우리는 상수만 채워 보낸다(메시지 타입상 생략 불가).

| 토픽 | 크기 | 29 Hz 일 때 | 50 Hz 일 때 |
|---|---|---|---|
| `/wheel_odom` | ~720 B | 20.9 kB/s | 36.0 kB/s |
| `/imu/data_raw` | ~330 B | 9.6 | 16.5 |
| `/imu/mag` | ~130 B | 3.8 | 6.5 |
| `/rover/status` | ~280 B | 1.4 (5 Hz 고정) | 1.4 |
| `/battery` | ~100 B | 0.1 (1 Hz 고정) | 0.1 |
| **합계** | | **35.8 kB/s (상한의 ~95%)** | **60.5 kB/s (상한의 ~150%)** |

당시 나는 "29 Hz 동작이 이미 상한의 95% 라 여유가 없었다" 고 적었다. §10 에서 반증된다.

### 방아쇠

`App/app/imu_processor.c:110` — `s_si.valid` 는 매 주기 SPI `imu_read()` 성공 여부에 달려 있어 간헐적이다.

- 09:52 첫 측정: `/imu/data_raw` 0.98 Hz 일 때 `/wheel_odom` 26.2 Hz **정상**
- 이후 imu 가 50 Hz 로 올라가자 odom 이 0 으로 밀림

즉 **보드 IMU 가 살아날 때마다 수요가 1.5 배로 뛰고, 가장 큰 메시지인 odom 이 먼저 굶는다.**
관측된 교대 점유가 바로 이 경쟁이다.

### 당시 그렸던 인과 연쇄 (§6.5 에서 무너짐)

```
USB FS 32B 엔드포인트 상한 (~38 kB/s)
  → 보드 발행 수요 최대 60.5 kB/s 로 초과
  → 가장 큰 메시지 /wheel_odom 이 수십 초 단위로 소실
  → sensor_conditioner 의 /wheel_odom/conditioned 중단
  → EKF 가 유일한 속도 관측을 잃고 카메라 IMU 가속도만 적분
  → 위치 8.5 m 발산
  → planner 가 유효 경로 생성 실패 → Nav2 ABORTED
```

## 6.5 대역 가설의 붕괴

게이트 적용 후 총수요를 22.4 kB/s 까지 낮췄는데도 odom 은 계속 0 이었다.
심지어 수요가 2 kB/s 인 구간에서도 0 이었다. 대역이 원인이라면 있을 수 없다.

이후 계측으로 위치를 좁혔다.

| 계측 | 결과 | 배제되는 것 |
|---|---|---|
| agent `-v6` 로그 | `recv_message` 1020 = DDS `write` 1020 | agent 는 받은 것을 버리지 않음 |
| `/rover/status` 에 실은 발행 카운터 | odom 시도 25/s, 실패 0, `rc=0` | rcl/버퍼/MTU 문제 아님 |
| 전송 계층 계측(`wb/wh/wf`) | 전부 0, 링 최대 점유 1559/8192 B | 보드는 모든 바이트를 정상 송신 |

남는 구간은 **STM32 UART → CH340 → USB** 뿐이었다. `HwFlowCtl = UART_HWCONTROL_NONE` 이라
CH340 이 보드를 막을 수단이 없다. baudrate 를 460800 으로 낮추자:

```
2,000,000 bps : odom 시도 25/s → 수신 0~13 Hz, 30초 단위로 전멸 반복
  460,800 bps : odom 시도 25/s → 수신 25.0 Hz, 70초 연속 100%, 드롭 0
```

전 토픽이 규정 주기로 복귀했다(odom 25.005 / imu 5.000 / mag 5.000 / status 5.000 /
battery 1.000 / conditioned 25.018 / filtered 30.003). `dmesg` 에 ch341 오류 보고는 없다 —
커널이 관측할 수 없는 CH340 칩 내부 유실과 일관된다.

## 8. 회피 주행 검증 — 완료 (job119 → job124)

링크가 안정된 뒤 09-08 부터 미뤄졌던 검증을 수행했다.

### job119 (lookahead 0.35) — 접촉 없이 중단

```
결과 CANCELED  주행 0.99m / 목표 1.80m
  최소 여유 28.7cm (접촉 0) | 횡오차 RMS 2.5cm 최대 7.0cm | ω 부호반전 0회
```

중단 연쇄 (nav2 로그):
```
RegulatedPurePursuitController detected collision ahead!  → follow_path 중단 (2회)
behavior_server: Running backup                            → 후진 복구
stuck_monitor: 지령 6.5cm/1° 인데 관측 0.8cm/1.7° (비율 0.12) → 목표 취소
```

상자를 밀지 않고 스스로 멈췄다 — 09-08 과 달리 안전 로직이 의도대로 동작했다.
원인: t=12~15s 의 ω 지령이 −0.099→−0.146→−0.116 (우회전, 목표 방향 복귀 구간)인데
RPP 충돌검사가 그 순간 곡률로 0.40 m(=5.0 s × 0.08 m/s)를 투영하면 상자를 스친다.
같은 x 에서 계획은 +0.315 인데 로버는 +0.230 — **8.5 cm 안쪽으로 코너 컷** 한 상태였다.

### 조정 — 실제 손잡이는 lookahead_dist 가 아니었다

`use_velocity_scaled_lookahead_dist: true` 이므로 실효 lookahead 는
`clamp(v × lookahead_time, min, max) = clamp(0.08×2.0=0.16, 0.35, 0.60) = 0.35`,
즉 **`min_lookahead_dist` 가 실제 값**이고 `lookahead_dist: 0.40` 은 이 속도에서 쓰이지 않았다.
(처음에 `lookahead_dist` 를 지목했다가 정정.) → `min_lookahead_dist` 0.35 → **0.25**.

함께 적용: `stuck_monitor` 가 Nav2 복구 행동(backup/spin/…) 실행 중에는 판정을 보류하도록
`/<behavior>/_action/status` 를 구독해 EXECUTING 이면 관측 창(W)만큼 보류.
근거: 후진 복구는 원래 느린데 정체로 오판하면 복구 기회 자체를 뺏는다.

### job124 (lookahead 0.25) — 완주

```
결과 SUCCEEDED  소요 32.8s  주행 1.98m
  최소 여유 28.0cm (접촉 0) | 횡오차 RMS 2.0cm 최대 4.6cm
  최대 좌측 변위 +33.8cm | ω 부호반전 4회 = 2.0회/m | 최종 위치오차 14.3cm
```

무주행 경로 질의: 최대 횡변위 +0.456 m(좌), 비용 최대 80 → 최근접 0.253 m,
**패딩 포함 차체 외곽에서 6.8 cm 여유**. 평균 비용 12 로 대부분 구간은 넓다.

| 지표 | job119 (0.35) | job124 (0.25) |
|---|---|---|
| 결과 | CANCELED 0.99 m | **SUCCEEDED 1.98 m** |
| 최소 여유 | 28.7 cm | 28.0 cm |
| 횡오차 RMS / 최대 | 2.5 / 7.0 cm | **2.0 / 4.6 cm** |
| 코너 컷 | 8.5 cm | 12 cm |
| ω 부호반전 | 0 회 | **2.0 회/m** |

**대가는 조향 진동이다.** 부호반전 0 → 2.0회/m 는 09-08 에 지적된 "까딱까딱" 증상의 재발이다.
추종 정확도(횡오차)와 조향 부드러움은 lookahead 를 사이에 둔 트레이드오프이며,
현재는 완주를 얻고 진동을 일부 내준 상태다. 중간값(0.30) 탐색은 미실행.

`stuck_monitor` 의 복구 중 억제 로직은 이번 주행에서 복구 행동이 발생하지 않아 **미검증**.

## 8.6 계측을 고치니 원인이 두 개 더 드러났다 (job125~job129)

job124 를 "접촉 0, 최소 여유 28.0cm" 로 보고했으나 **틀렸다.** 사용자가 "상자에 너무 가까이
붙어서 움직였다" 고 지적해 CSV 로 기하 계산한 결과:

```
상자(주행 직전 서베이): x 1.033~1.143, y -0.046~+0.134
실제 최근접(차체 외곽↔상자 외곽): 0.0 cm — 차체 좌측 끝 +0.132, 상자 좌측 끝 +0.134
```

**왜 틀렸나**: '최소 여유' 를 실시간 깊이 포인트클라우드의 최근접 점으로 쟀다. 로버가 상자 **옆을**
지나기 시작하면 상자가 카메라 화각을 벗어나 그 값이 멀리 있는 다른 물체로 바뀐다.
실제로 t=16 에 nan, t=17 에 1.211 로 튄다. **옆을 지나는 간격을 전방 카메라로 재려 한 설계 자체가 틀렸다.**
→ job125 에서 출발 시 map 에 고정한 상자 사각형 ↔ 차체 사각형의 **기하 거리**로 교체(카메라 무관).

동시에 "코너 컷" 진단도 철회한다. 주행 중 횡오차는 RMS 2.0cm 로 작았다 — 컨트롤러는 **그때의**
경로를 잘 따랐다. 주행 전 질의로 얻은 경로와 비교한 것이 오류였다(Nav2 는 계속 재계획한다).

### 원인 A — 전역 경로의 좌우 양안정성 (job126)

```
  t   | 계획여유 계획횡 | lc_box gc_box | v_cmd  w_cmd
  7.0 |    0.082 +0.389 |   100    99 | +0.080 -0.014
  8.0 |    0.001 -0.216 |   100    99 | +0.000 -0.320   ← 우측으로 뒤집힘, 여유 0.001m
  9.0 |    0.110 +0.410 |   100    99 | +0.000 +0.320   ← 다시 좌측
```

상자가 거의 정중앙이라 좌회피·우회피 비용이 거의 같고, 코스트맵이 조금만 갱신되면 선택이 뒤집힌다.
뒤집힐 때마다 방위 오차가 `rotate_to_heading_min_angle`(0.5 rad)을 넘어 RPP 가 **전진을 멈추고
제자리 회전**한다(v=0, |ω|=0.320). **사용자가 본 "까딱까딱" 의 정체** — 컨트롤러 이득이 아니라
계획이 흔들린 것이었다.

**조치**: `footprint_padding` 0.02 → 0.05. 뒤집힌 경로의 여유가 0.001m 였다는 것은 그것이
내접반경 바로 바깥을 스치며 통과 판정을 받았다는 뜻이다. 통과 가능 여부는 inflation 이 아니라
내접반경(반폭 0.165 + 패딩)이 정하므로, 패딩을 올려 그런 경로를 계획 단계에서 배제한다(내접 0.215).
**결과**: 무주행 질의 3회 연속 동일 경로, job128 에서도 t=14 까지 계획 횡좌표 +0.35~+0.40 안정.

### 원인 B — 라이다가 자기가 볼 수 없는 것을 지운다 (job128)

```
  t   | 실여유 계획여유 계획횡 | lc_box gc_box
 13.0 |  0.130    0.118 +0.379 |    99    99
 14.0 |  0.115   -0.102 +0.163 |    99     0
 15.0 |  0.083   -0.060 +0.206 |     0     0   ← 상자 소실
 17.0 |  0.000   -0.055 +0.212 |     0     0   ← 접촉
```

t=14 에 상자가 코스트맵에서 지워지고 **그 즉시 계획 여유가 음수(−10.2cm)** 가 되어 경로가 상자를
관통했다. 기하로 기전을 확정:

```
로버 중심 전진 0.692, 상자 전면 map x 1.071
  카메라까지 1.071 − 0.692 − 0.232 = 0.147 m  → D455f 최소 깊이 안쪽, 못 봄
  라이다까지 1.071 − 0.692 − 0.152 = 0.227 m  → scan 의 raytrace_min_range 0.2 를 넘음
```

라이다는 z 0.185 라 높이 0.11m 상자를 **원리적으로 볼 수 없는데**, 그 셀을 관통해 뒤쪽 벽까지
레이트레이스하며 카메라의 마킹을 자유 공간으로 되돌린다. 출발 시엔 카메라 마킹이 더 빨라 버티다가,
카메라가 실명하는 순간 소거만 남아 증발한다.

`raytrace_min_range` 를 카메라 기준(로컬 0.35/전역 0.30)으로 맞춰 뒀지만 **지우는 주체는
라이다(0.2)** 였다. 09-08 의 "근접 기억 반경을 센서 물리 사각과 일치시켰다" 는 카메라에만 적용됐었다.

**조치 — 레이어 분리** (파라미터 인상 대신 구조로):

```
local  plugins: ['voxel_layer', 'obstacle_layer', 'inflation_layer']
global plugins: ['static_layer', 'voxel_layer', 'obstacle_layer', 'inflation_layer']
  voxel_layer    : observation_sources: depth   (카메라 전용, VoxelLayer)
  obstacle_layer : observation_sources: scan    (라이다 전용, ObstacleLayer, combination_method 1)
```

레이어마다 자기 격자를 갖고 마스터는 Maximum 으로 합치므로, 라이다 레이어는 카메라 레이어의
마킹을 **낮출 수 없다**. '못 보는 것을 지운다' 는 상황이 구조적으로 불가능해진다.

**원칙**: 센서는 자기가 감지할 수 있는 것만 지울 수 있어야 한다. 레이어는 센서 **개수**가 아니라
**감지 가능한 부피**로 묶는다. 사각지대가 다르면 반드시 분리한다.
**대가**: 레이어를 나누면 그 마킹은 그 레이어의 센서만 되돌릴 수 있다 → 각 레이어에는 자기가 찍은
것을 지울 수 있는 센서가 반드시 있어야 한다. 마킹만 하는 센서를 단독 레이어에 두면 자국이 영구히 남는다.

### 남은 위험과 STVL 검토

분리 후 카메라 레이어의 마킹은 카메라만 지운다. 화각 약 87°, 최소 거리 0.35m 이므로 다시 볼 수 없는
셀은 남고, 로컬은 3×3m 롤링이라 사라지지만 **전역은 남는다**(유령).

스톡 `nav2_costmap_2d::VoxelLayer` 에는 **시간 감쇠가 없다**. 서비스로 흉내 낼 수는 있으나
`clear_around_*` 는 로버 **근처를** 지워 정반대이고, `clear_except_*` 는 거리 기준이라 뭉툭하다.

`spatio_temporal_voxel_layer` (STVL) 는 **미설치**이며 apt 로 설치 가능(2.3.4-1jammy).
`voxel_decay` + `decay_model` 로 시간 감쇠를, 절두체 기반 감쇠로 '화각 안에 있는데 재관측 안 됨'
을 구분해 처리한다. 깊이 카메라의 min/max z 와 화각을 직접 받으므로 최소측정거리 실명을 모델이 안다.

**기각한 대안**: 전역만 카메라+라이다를 합치고 로컬만 분리 — 유령은 사라지지만 **계획을 만드는 것이
전역**이므로 job128 의 관통 경로가 그대로 재현되고, 로컬이 막아 정지만 반복한다. 플래너가 제안한
경로를 컨트롤러가 항상 거부해야 하는 구조가 되어 설계로서 부적절.

**STVL 도입은 보류**. 유령이 실제로 문제인지 아직 측정하지 않았고(상자 제거 시험 미실행), 하루에
원인 세 개를 바꾼 직후라 변수를 더 늘리면 효과 귀속이 불가능하다.

## 8.7 레이어 분리는 원인이 아니었다 (job134, job135) — 정정

레이어 분리를 배포하고 같은 시험을 반복했다(job134, 상자를 우측으로 치워 좌측 여유 확보).
주행 전 질의는 3회 모두 좌측 +0.29, 비용 최대 72 → 최근접 0.319m = 차체 외곽 여유 15.4cm 로 양호했다.

그런데 결과는 **또 접촉**이고, 상자는 **또 지워졌다**.

```
  t   | 실여유 계획여유 계획횡 | lc_box gc_box
  4.0 |  0.437    0.006 +0.121 |   100    99
  5.0 |  0.363    0.005 +0.120 |   100     0   ← 전역이 먼저 소실
  9.0 |  0.198   -0.099 -0.003 |     0     0   ← 로컬도 소실
 12.0 |  0.000   -0.064 +0.059 |     0    83   ← 접촉
결과 SUCCEEDED  ① 실제 최근접 0.0cm  ② 계획 여유 최소 −10.9cm
```

live 파라미터로 분리가 실제 적용 중임을 확인했다(job135):

```
local  plugins: ['voxel_layer','obstacle_layer','inflation_layer']
  voxel_layer.observation_sources    = depth
  obstacle_layer.observation_sources = scan,  combination_method = 1
```

**따라서 지운 주체는 카메라 자신이다.** 이 레이어에서 소거 권한을 가진 소스는 depth 하나뿐이고,
마스터는 Maximum 합성이라 마스터가 0 이면 모든 레이어가 0 이다.

**§8.6 원인 B("라이다가 못 보는 것을 지운다")는 원인이 아니었다.** 라이다를 격리했는데도 같은 시점에
같은 방식으로 지워졌다. 레이어 분리 자체는 설계 원칙상 옳으므로 유지하지만, 접촉의 원인은 아니었다.

### 진짜 기전 — 카메라의 자기 소거

```
상자 중심 map x 1.021, 카메라 = base_link + 0.232
 t=5  전진 0.312 → 카메라~상자 0.48m   전역 raytrace_min_range 0.30 초과 → gc_box 100→0
 t=9  전진 0.503 → 카메라~상자 0.29m   로컬 0.35 근처       → lc_box 100→0
```

전역(0.30)이 먼저, 로컬(0.35)이 나중에 무너진다 — 값의 크기 순서와 정확히 일치한다.

09-08 에 이 값을 0.90 → 0.35 로 낮춘 근거는 "카메라 최소 측정거리 ≈0.22~0.25m 이므로 0.35 면 충분"
이었다. **그 전제가 틀렸다.** 실제 소거 기전은 '못 봐서' 가 아니라 **상자 옆·너머 바닥점으로 나가는
광선이 상자 셀을 스쳐 지나며 지우는 것**이라, 최소 측정거리와 무관하다. 좁은 물체(폭 0.18m) 주변에
넓은 바닥이 보이면 5cm 격자 양자화 때문에 일부 광선이 상자 셀을 통과한다.

**조치**: depth 의 `raytrace_min_range` 로컬 0.35 → **0.60**, 전역 0.30 → **0.60**.
관측된 소거 지점(0.29~0.48m)을 덮되 유령 반경은 09-08 의 0.90 보다 작게 둔다.
**검증 미실행** — 로버가 종료 지점에 있어 출발 배치 재설정이 필요하다.

## 8.8 결정적 실험 — 기전은 '소거' 가 아니라 '마킹 중단' (job152, job155)

### job152 — 오늘 처음 접촉 없이 완주

`raytrace_min_range` 0.60 적용, 상자를 우측으로 치워 좌측 여유 확보.

```
결과 SUCCEEDED  주행 1.56m
① 실제 최근접 4.1cm (접촉 없음)     ④ 경로 좌우 전환 0회
② 계획이 접촉 경로였던 샘플 0/234 (0%)   조향 부호반전 1.3회/m
③ gc_box t=5, lc_box t=7 에 0 — 여전히 지워짐
```

| 지표 | job134 | job141 | **job152** |
|---|---|---|---|
| 결과 | SUCCEEDED(접촉) | CANCELED | **SUCCEEDED** |
| 실제 최근접 | 0.0 cm | 38.7 cm(미완주) | **4.1 cm** |
| 계획이 접촉 경로 | 55% | 55% | **0%** |
| 경로 좌우 전환 | — | 0회 | **0회** |

패딩 0.05 로 양안정성이 잡혔고, 여유가 충분한 배치에서는 **상자가 지워져도 완주**한다.
다만 소거 자체는 남았고, 기하상 그 시점 카메라~상자는 0.518m 로 `raytrace_min_range` 0.60
**안쪽**이라 소거가 막혔어야 했다 — 값은 live 확인 결과 로컬·전역 모두 0.6 이었다.

### job155 — `clearing: false` 로 갈랐다

소거가 기전인지 마킹 중단이 기전인지 가르기 위해 카메라 소거를 **완전히 껐다**.

```
clearing: false 인데도
 t=3  lc_box 0   t=6  100   t=11  0   t=12  99   t=13  0  …  t=15 이후 계속 0
결과 CANCELED, ① 실제 최근접 0.0cm, ② 계획 최소 여유 −16.1cm
```

**소거가 불가능한 상태에서 셀 값이 100 ↔ 0 을 오갔다.** Nav2 는 매 주기 마스터 코스트맵을
리셋하고 각 레이어로 다시 그리므로, 레이어 격자에 그 순간 마킹이 없으면 마스터도 0 이 된다.
즉 **지워지는 것이 아니라 마킹이 끊기는 것**이다.

### 이 실험 하나로 기각된 가설들

| 가설 | 조치 | 결과 |
|---|---|---|
| 라이다가 못 보는 것을 지운다 (§8.6 원인 B) | 레이어 분리 | 그대로 사라짐 |
| 카메라가 근접 시 자기 마킹을 지운다 (§8.7) | raytrace_min_range 0.35/0.30 → 0.60 | 그대로 사라짐 |
| 소거 자체가 기전이다 | **clearing: false** | **그대로 사라짐 → 기각** |

남는 것은 하나 — **로버가 가까워지면 카메라가 상자에 대한 깊이점을 안정적으로 만들지 못해
마킹이 끊긴다.** 09-08 에 `mark_threshold` 를 1→0 으로 내리며 "가까워지면 윗면만 보여
복셀 1칸" 이라 관측했던 것과 같은 계열이고, 그때의 조치로는 부족했다.

### 해법의 방향이 바뀐다

지금까지 '덜 지우게' 만들려 했으나, 필요한 것은 **'관측이 끊겨도 유지되는 기억'** 이다.
이는 파라미터가 아니라 레이어의 기능이며, 스톡 `nav2_costmap_2d::VoxelLayer` 에는
'마지막 관측 이후 유지' 개념이 없다. **STVL(`spatio_temporal_voxel_layer`) 의
voxel decay / persistence 가 정확히 이 문제를 위한 기능**이다(미설치, apt 로 설치 가능).

`clearing: false` 는 진단 전용이었으므로 되돌렸다.

## 8.9 DDS 공유메모리 사고 — 내가 만든 문제 (job144~151)

주행 중 로버가 "지도를 벗어나 이상하게 움직인다" 는 보고를 받고 조사한 결과:

```
/odometry/filtered  Publisher count: 0     ← EKF 노드는 살아있는데 퍼블리셔가 그래프에서 사라짐
ekf_node  살아있음 CPU 20% 상태 Sl, 입력 정상(/wheel_odom/conditioned 25Hz, /imu/data 199.7Hz)
타임스탬프 오프셋 −0.002~−0.032s, 역행 0회   ← 시각 동기 문제 아님

[RTPS_TRANSPORT_SHM Error] Failed init_port fastrtps_port7423: open_and_lock_file failed
/dev/shm/fastrtps_port7423     → 없음
/dev/shm/fastrtps_port7423_el  → 존재            ← 잠금 파일만 남은 고아
```

FastDDS 는 같은 호스트에서 공유메모리 전송을 쓰고, 정상 종료 시 SHM 세그먼트와 잠금 파일을
정리한다. **`SIGKILL` 을 받으면 정리하지 못한다.** 그러면 다음 참가자가 같은 포트를 열 때
`open_and_lock_file failed` 로 실패하고 퍼블리셔가 그래프에 등록되지 못한다.

**나는 오늘 `pkill -9` 를 반복해서 썼다**(job97·100·101·102·104·115·121·122·123·127·129·132·143).
"정리를 확실히" 하려던 것이 DDS 관점에서는 정리를 못 하게 만드는 신호였다.

설명되는 증상: EKF 가 TF 를 못 냄 → map 좌표가 얼어붙음 → SLAM 이 `/map` 을 못 냄 →
코스트맵이 `Message Filter dropping message: frame 'camera_depth_optical_frame' / 'lidar_link'`
로 **라이다·카메라를 둘 다 버림** → 계획·복구가 엉킴.
보드 토픽만 멀쩡했던 이유는 에이전트 컨테이너에 `MICROROS_DISABLE_SHM=1` 이 설정돼 있어서다.

**복구 검증** — SIGTERM 정상 종료 + `/dev/shm/fastrtps*` 15개 삭제 후:

| 항목 | 고장 시 | 복구 후 |
|---|---|---|
| `/odometry/filtered` | 퍼블리셔 0, 무발행 | 퍼블리셔 1, 30.007 Hz |
| `/tf` | 무발행 | 퍼블리셔 4, 47.4 Hz |
| `/map` | 무발행 | 퍼블리셔 1, 0.500 Hz |

**재발 방지**: ROS 노드 정리는 `pkill -TERM` → 최대 15초 대기 → 남은 것만 `-9`.
`job154_reinit.sh`, `job156_stop.sh` 는 이 방식으로 작성했고 실제로 SIGTERM 만으로 잔존 0 이었다.

> 참고: 앞서 "SLAM 정합이 어긋났다" 고 적었던 것은 **틀렸다**. SLAM 은 정합에 실패한 것이 아니라
> 입력 TF 자체를 못 받아 아무 것도 못 한 것이다. 또 보드 `/wheel_odom` 의 x=1.614 를 map 좌표와
> 비교해 '헛돌았다' 고 본 것도 오류다 — 보드 오도메트리는 **보드 리셋 이후 누적값**이고
> map 좌표는 `job123_reinit` 이후의 상대값이라 기준이 다르다.

## 8.11 STVL 도입 (job160~166)

§8.8 에서 기전이 '마킹 중단' 으로 확정됐고, 스톡 `VoxelLayer` 에는 '마지막 관측 시각' 개념이
없으므로 파라미터로는 해결되지 않는다. 사용자 판단으로 STVL 도입.

### 설치

```
sudo apt-get install -y ros-humble-spatio-temporal-voxel-layer   (사용자에게 사전 고지)
→ spatio_temporal_voxel_layer 2.3.4 + ros-humble-openvdb-vendor
플러그인 클래스: spatio_temporal_voxel_layer/SpatioTemporalVoxelLayer
```

파라미터 이름은 **추측하지 않고** 설치본에서 확인했다 — 라이브러리 심볼 추출 + 함께 설치된
공식 예제 `example/constrained_indoor_environment_config.yaml`.

### 구성 — 공식 실내 예제의 '마킹/소거 소스 분리' 패턴

```
plugins: local  ['stvl_layer', 'obstacle_layer', 'inflation_layer']
         global ['static_layer', 'stvl_layer', 'obstacle_layer', 'inflation_layer']

stvl_layer (양쪽 동일)
  voxel_decay 15.0 / decay_model 0(선형) / voxel_size 0.05 / mark_threshold 0
  combination_method 1 (Maximum — 라이다 레이어가 이 마킹을 낮출 수 없다)
  observation_sources: depth_mark depth_clear      ← 같은 토픽을 두 소스로 분리
  depth_mark : marking true / clearing false / obstacle_range 1.2 / min_obstacle_height 0.06
  depth_clear: marking false / clearing true
               min_z 0.25  max_z 1.5
               vertical_fov_angle 1.012(58°)  horizontal_fov_angle 1.518(87°)
               decay_acceleration 3.0  model_type 0(depth camera)
```

**핵심은 `min_z: 0.25`** — 카메라 실측 최소 측정거리(job71: 0.25m 288점 / 0.21m 8점)를
절두체 근평면으로 준다. 이보다 가까운 복셀은 절두체 **밖**이라 가속 감쇠를 받지 않으므로,
로버가 다가가 카메라가 실명하는 구간에서 상자가 그대로 남는다. 이것이 노린 효과다.

동적 장애물 망각은 `decay_acceleration` 이 담당한다 — 절두체 **안**인데 재관측되지 않으면
더 빨리 지운다. 즉 **'볼 수 있는데 없다' 와 '못 본다' 를 구분**한다. 스톡 VoxelLayer 는
이 구분이 불가능했고, 그것이 09-08 부터 반복된 문제의 뿌리였다.

### 겪은 오류 1건 (기록)

첫 배포에서 `planner_server` 가 exit 255 로 죽었다:
`FATAL: Can not get 'plugin' param value for static_layer`.
YAML 에서 `static_layer:` 와 `voxel_layer:` 가 인접해 있었는데, 교체 스크립트가
`plugins:` 줄부터 다음 마커까지를 잘라내며 **static_layer 블록까지 지웠다.**
복구 후 "plugins 에 나열된 모든 레이어에 plugin 키가 있는가" 를 YAML 파싱으로 검증하는
절차를 추가했다.

### 결과

```

global_costmap: 동일
전 노드 active, 코스트맵 발행 1.667 / 0.667 Hz, 오류 없음
```

**배제된 것**: 펌웨어 DMA/타이머 설정(`dma.c`·`tim.c` 09-01 이후 커밋 없음, USART1 RX=DMA2_Stream2 /

agent 드롭 · 보드 전송 실패.

**남은 후보**:
1. 물리 계층 — 커넥터 접촉, 케이블 경로. WT-600 이관으로 배선이 바뀌었다.
2. **09-07 모터 PWM 50 Hz → 20 kHz.** 그 구간의 가장 큰 전기적 변화이고 이상은 직후에 나타났다.
   단, 오늘 장애는 모터 정지 상태에서도 발생해 단순 EMI 로는 완전히 설명되지 않는다.
3. CH340 모듈 또는 젯슨 ch341 벤더 드라이버 상태.

**좁히는 절차 (미실행)**: ① `dmesg` ch341 오류 — 확인 완료, 보고 없음 ② USB 포트·케이블 교체 후
2 Mbps 재시험 ③ 모터 구동 중 vs 정지 중 2 Mbps 손실률 비교(PWM EMI 판정) ④ 09-06 펌웨어 A/B.

**소급 영향**: 09-08 의 미해결 이상(1.40 m 목표에 5.79 m 경로, SLAM map yaw 점프,
여유가 있는데 상자에 붙는 경로)이 odom 간헐 소실의 약한 증상이었을 가능성이 있다.
당시 코스트맵 파라미터로 설명했는데, 그 설명이 전부 틀렸다는 뜻은 아니지만 **오염 가능성은 인정한다.**
링크가 안정된 지금 재검증이 필요하다.

## 9. 이 날 배운 것

1. **"잘 맞아떨어지는 숫자" 하나로 인과를 단정하지 말 것.** USB 32 B 엔드포인트에서 계산한
   32~40 kB/s 가 관측 최대치 36.6 kB/s 와 일치해서 확신했지만, 그건 우연이었다.
   과거 로그(60 kB/s)를 5 분만 확인했으면 즉시 반증됐을 것이다.
   **새 이론을 세우면 과거 측정치와 먼저 대조한다.**
2. **"어제까지 됐다"는 정보는 가설을 절반으로 줄인다.** 사용자의 질의가 없었으면 나는 잘못된
   용량 한계 이론을 그대로 커밋해 두었을 것이다. 회귀인지 한계인지부터 가르는 것이 순서다.
3. **best-effort 는 실패를 알려주지 않는다.** `rcl_publish` 가 rc=0 을 돌려주는데도 데이터가
   사라졌다. 계층별 계측(rcl / 전송 / agent / DDS)을 넣어 구간을 좁히기 전까지는
   모든 가설이 그럴듯해 보였다. **계측 없는 추론은 비용만 든다.**
4. **부분 실패는 크기 순으로 온다.** 작은 메시지가 정확한 주기를 유지하는데 큰 메시지만 사라지는
   비대칭이 원인 구간을 좁히는 가장 강한 단서였다.
5. **도구의 정규식 방언을 확인할 것.** `pkill -f "a\|b"` 는 ERE 에서 리터럴이다. 정리 스크립트가
   조용히 실패해 측정 두 건을 오염시켰다.
