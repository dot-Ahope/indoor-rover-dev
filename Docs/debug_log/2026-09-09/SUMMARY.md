# 2026-09-09 — micro-ROS 링크에서 /wheel_odom 이 사라진 문제

## 0. 이 날의 결론

`/wheel_odom`(732 B) 이 수십 초씩 통째로 사라져 EKF 가 8.5 m 발산하고 Nav2 가 ABORTED 되었다.
**baudrate 를 2,000,000 → 460,800 으로 낮추자 70 s 연속 100% 전달·드롭 0 으로 해소**되었다.

⚠ **이것은 우회이지 근본 해결이 아니다.** 같은 2 Mbps 설정으로 2026-08-27 에는
`/wheel_odom` 49.995 Hz + `/imu/data_raw` 49.999 Hz(≈60 kB/s)가 안정적으로 나왔다.
즉 용량 한계가 아니라 **08-27 이후 생긴 회귀**이며 원인은 아직 미확정이다.

> 이 문서는 하루 동안 세운 가설을 순서대로 남긴다. §6 의 'USB 32 B 엔드포인트가 상한' 결론은
> **틀렸고** §10 에서 반증·정정한다. 틀린 추론을 지우지 않고 남기는 이유는, 어떤 근거로
> 잘못 확신했는지가 결과만큼 중요하기 때문이다.

## 2. 무주행 경로 질의 — 설정 변경 자체는 의도대로 동작 (job91)

장면: 상자가 정면 1.00 m, base_link 기준 y −0.10~+0.20, z 중앙 0.08. 라이다는 상자를 못 보고 정면 243 cm,
좌30° 127 cm / 우30° 78 cm (왼쪽이 넓음).

`job91_query.py 1.80` (Nav2 `compute_path_to_pose` 직접 질의, 주행 없음):

```
경로 길이 2.75m / 직선 1.80m (+52.9%)
최대 횡변위 +0.488m (좌) @ 전방 0.63m
x=0.99m(상자 위치) → y=+0.410m
경로 비용 최대 71 (OccupancyGrid 0~100 스케일)
```

**비용 71 의 해석**: Nav2 `Costmap2DPublisher` 는 내부 0~255 비용을 0~100 으로 축약해 발행한다
(`v = 1 + 97*(i-1)/251`). 역산하면 i ≈ 182. 인플레이션 비용 모델
`cost = 252·exp(−cost_scaling·(d − r_inscribed))` 에 global 값(scaling 3.0, r_inscribed = 반폭 0.165 + 패딩 0.02 = 0.185)
을 넣으면

```
d = 0.185 + ln(252/182)/3.0 = 0.185 + 0.109 = 0.294 m
```

즉 경로의 최근접 장애물 거리 0.294 m, **패딩 포함 차체 외곽에서 10.9 cm 여유**. 상자 왼쪽 끝(+0.20)과
경로 중심(+0.41) 사이 21 cm 와도 일치한다. 09-08 job89 에서 경로가 상자에 붙어 접촉했던 것과 대비되는,
의도한 거동이다.

> ⚠ 단, 이건 **플래너의 계획**이다. 실제 접촉 여부는 컨트롤러(RPP)가 그 경로를 얼마나 따라가느냐에 달렸고,
> 그 주행 검증은 아래의 링크 장애 때문에 **오늘도 완료하지 못했다.**

## 6. [정정됨 — §10 참조] 당시 세운 결론: 병목은 UART 가 아니라 USB (job106, job107)

```
/dev/rover → ttyCH341USB0        (CH340, 1a86:7523)   ← 보드
/dev/rplidar → ttyUSB0           (CP2102N, 10c4:ea60) ← 라이다 (드라이버 cp210x)
agent Cmd: serial --dev /dev/rover -b 2000000

USB 장치 /sys/bus/usb/devices/1-2.1/   speed = 12 Mbps  (Full Speed)
  ep_02 : wMaxPacketSize = 0x20 (32 B), type Bulk    ← OUT
  ep_82 : wMaxPacketSize = 0x20 (32 B), type Bulk    ← IN
  ep_81 : wMaxPacketSize = 0x08,        type Interrupt, interval 1ms
```

당시 나는 이렇게 계산했다: USB Full-Speed 벌크는 1 ms 프레임 단위이고 엔드포인트가 32 B 이므로
실효 상한 약 32~40 kB/s. 관측 최대치(odom 단독 50.9 Hz × 720 B = 36.6 kB/s)와 맞아떨어져 확신했다.

**이 결론은 틀렸다.** 08-27 실측 60 kB/s 가 반증한다(§10). 36.6 kB/s 는 상한이 아니라
그 시점의 우연한 값이었고, 나는 '맞아떨어지는 숫자' 하나로 인과를 단정했다.

`2,000,000 bps` 는 **UART 구간의 선로 속도**일 뿐이고 200 kB/s 의 여유는 쓸 수 없다.
나는 그동안 이 여유가 있다고 잘못 알고 있었다.

### 대역 수지

메시지 크기는 CDR 직렬화 기준. `nav_msgs/Odometry` 는 pose 7 double(56) + 공분산 36 double(288)
+ twist 6 double(48) + 공분산 36 double(288) = 680 B + 헤더/프레임 문자열 ≈ 720 B.
**공분산 576 B 가 전체의 80%** 인데 우리는 상수만 채워 보낸다(메시지 타입상 생략 불가).

| 토픽 | 크기 | 29 Hz 일 때 | 50 Hz 일 때 |
|---|---|---|---|
| `/wheel_odom` | ~720 B | 20.9 kB/s | 36.0 kB/s |
| `/imu/data_raw` | ~330 B | 9.6 | 16.5 |
| `/imu/mag` | ~130 B | 3.8 | 6.5 |
| `/rover/status` | ~280 B | 1.4 (5 Hz 고정) | 1.4 |
| `/battery` | ~100 B | 0.1 (1 Hz 고정) | 0.1 |
| **합계** | | **35.8 kB/s (상한의 ~95%)** | **60.5 kB/s (상한의 ~150%)** |

당시 나는 "29 Hz 동작이 이미 상한의 95% 라 여유가 없었다" 고 적었다. §10 에서 반증된다.

### 방아쇠

`App/app/imu_processor.c:110` — `s_si.valid` 는 매 주기 SPI `imu_read()` 성공 여부에 달려 있어 간헐적이다.

- 09:52 첫 측정: `/imu/data_raw` 0.98 Hz 일 때 `/wheel_odom` 26.2 Hz **정상**
- 이후 imu 가 50 Hz 로 올라가자 odom 이 0 으로 밀림

즉 **보드 IMU 가 살아날 때마다 수요가 1.5 배로 뛰고, 가장 큰 메시지인 odom 이 먼저 굶는다.**
관측된 교대 점유가 바로 이 경쟁이다.

### 당시 그렸던 인과 연쇄 (§6.5 에서 무너짐)

```
USB FS 32B 엔드포인트 상한 (~38 kB/s)
  → 보드 발행 수요 최대 60.5 kB/s 로 초과
  → 가장 큰 메시지 /wheel_odom 이 수십 초 단위로 소실
  → sensor_conditioner 의 /wheel_odom/conditioned 중단
  → EKF 가 유일한 속도 관측을 잃고 카메라 IMU 가속도만 적분
  → 위치 8.5 m 발산
  → planner 가 유효 경로 생성 실패 → Nav2 ABORTED
```

## 6.5 대역 가설의 붕괴

게이트 적용 후 총수요를 22.4 kB/s 까지 낮췄는데도 odom 은 계속 0 이었다.
심지어 수요가 2 kB/s 인 구간에서도 0 이었다. 대역이 원인이라면 있을 수 없다.

이후 계측으로 위치를 좁혔다.

| 계측 | 결과 | 배제되는 것 |
|---|---|---|
| agent `-v6` 로그 | `recv_message` 1020 = DDS `write` 1020 | agent 는 받은 것을 버리지 않음 |
| `/rover/status` 에 실은 발행 카운터 | odom 시도 25/s, 실패 0, `rc=0` | rcl/버퍼/MTU 문제 아님 |
| 전송 계층 계측(`wb/wh/wf`) | 전부 0, 링 최대 점유 1559/8192 B | 보드는 모든 바이트를 정상 송신 |

남는 구간은 **STM32 UART → CH340 → USB** 뿐이었다. `HwFlowCtl = UART_HWCONTROL_NONE` 이라
CH340 이 보드를 막을 수단이 없다. baudrate 를 460800 으로 낮추자:

```
2,000,000 bps : odom 시도 25/s → 수신 0~13 Hz, 30초 단위로 전멸 반복
  460,800 bps : odom 시도 25/s → 수신 25.0 Hz, 70초 연속 100%, 드롭 0
```

전 토픽이 규정 주기로 복귀했다(odom 25.005 / imu 5.000 / mag 5.000 / status 5.000 /
battery 1.000 / conditioned 25.018 / filtered 30.003). `dmesg` 에 ch341 오류 보고는 없다 —
커널이 관측할 수 없는 CH340 칩 내부 유실과 일관된다.

## 8. 회피 주행 검증 — 완료 (job119 → job124)

링크가 안정된 뒤 09-08 부터 미뤄졌던 검증을 수행했다.

### job119 (lookahead 0.35) — 접촉 없이 중단

```
결과 CANCELED  주행 0.99m / 목표 1.80m
  최소 여유 28.7cm (접촉 0) | 횡오차 RMS 2.5cm 최대 7.0cm | ω 부호반전 0회
```

중단 연쇄 (nav2 로그):
```
RegulatedPurePursuitController detected collision ahead!  → follow_path 중단 (2회)
behavior_server: Running backup                            → 후진 복구
stuck_monitor: 지령 6.5cm/1° 인데 관측 0.8cm/1.7° (비율 0.12) → 목표 취소
```

상자를 밀지 않고 스스로 멈췄다 — 09-08 과 달리 안전 로직이 의도대로 동작했다.
원인: t=12~15s 의 ω 지령이 −0.099→−0.146→−0.116 (우회전, 목표 방향 복귀 구간)인데
RPP 충돌검사가 그 순간 곡률로 0.40 m(=5.0 s × 0.08 m/s)를 투영하면 상자를 스친다.
같은 x 에서 계획은 +0.315 인데 로버는 +0.230 — **8.5 cm 안쪽으로 코너 컷** 한 상태였다.

### 조정 — 실제 손잡이는 lookahead_dist 가 아니었다

`use_velocity_scaled_lookahead_dist: true` 이므로 실효 lookahead 는
`clamp(v × lookahead_time, min, max) = clamp(0.08×2.0=0.16, 0.35, 0.60) = 0.35`,
즉 **`min_lookahead_dist` 가 실제 값**이고 `lookahead_dist: 0.40` 은 이 속도에서 쓰이지 않았다.
(처음에 `lookahead_dist` 를 지목했다가 정정.) → `min_lookahead_dist` 0.35 → **0.25**.

함께 적용: `stuck_monitor` 가 Nav2 복구 행동(backup/spin/…) 실행 중에는 판정을 보류하도록
`/<behavior>/_action/status` 를 구독해 EXECUTING 이면 관측 창(W)만큼 보류.
근거: 후진 복구는 원래 느린데 정체로 오판하면 복구 기회 자체를 뺏는다.

### job124 (lookahead 0.25) — 완주

```
결과 SUCCEEDED  소요 32.8s  주행 1.98m
  최소 여유 28.0cm (접촉 0) | 횡오차 RMS 2.0cm 최대 4.6cm
  최대 좌측 변위 +33.8cm | ω 부호반전 4회 = 2.0회/m | 최종 위치오차 14.3cm
```

무주행 경로 질의: 최대 횡변위 +0.456 m(좌), 비용 최대 80 → 최근접 0.253 m,
**패딩 포함 차체 외곽에서 6.8 cm 여유**. 평균 비용 12 로 대부분 구간은 넓다.

| 지표 | job119 (0.35) | job124 (0.25) |
|---|---|---|
| 결과 | CANCELED 0.99 m | **SUCCEEDED 1.98 m** |
| 최소 여유 | 28.7 cm | 28.0 cm |
| 횡오차 RMS / 최대 | 2.5 / 7.0 cm | **2.0 / 4.6 cm** |
| 코너 컷 | 8.5 cm | 12 cm |
| ω 부호반전 | 0 회 | **2.0 회/m** |

**대가는 조향 진동이다.** 부호반전 0 → 2.0회/m 는 09-08 에 지적된 "까딱까딱" 증상의 재발이다.
추종 정확도(횡오차)와 조향 부드러움은 lookahead 를 사이에 둔 트레이드오프이며,
현재는 완주를 얻고 진동을 일부 내준 상태다. 중간값(0.30) 탐색은 미실행.

`stuck_monitor` 의 복구 중 억제 로직은 이번 주행에서 복구 행동이 발생하지 않아 **미검증**.

따라서 §6 의 '실효 상한 32~40 kB/s' 는 반증되고, "이 링크는 원래 상한의 95% 에서 아슬아슬하게
돌고 있었다" 는 서술도 폐기한다. 오늘의 장애는 **08-27 과 09-09 사이에 생긴 회귀**다.

**배제된 것**: 펌웨어 DMA/타이머 설정(`dma.c`·`tim.c` 09-01 이후 커밋 없음, USART1 RX=DMA2_Stream2 /
TX=DMA2_Stream7 그대로, 충돌 스트림 추가 없음) · CPU 부하 · 메시지 크기/스트림 버퍼 ·
agent 드롭 · 보드 전송 실패.

**남은 후보**:
1. 물리 계층 — 커넥터 접촉, 케이블 경로. WT-600 이관으로 배선이 바뀌었다.
2. **09-07 모터 PWM 50 Hz → 20 kHz.** 그 구간의 가장 큰 전기적 변화이고 이상은 직후에 나타났다.
   단, 오늘 장애는 모터 정지 상태에서도 발생해 단순 EMI 로는 완전히 설명되지 않는다.
3. CH340 모듈 또는 젯슨 ch341 벤더 드라이버 상태.

**좁히는 절차 (미실행)**: ① `dmesg` ch341 오류 — 확인 완료, 보고 없음 ② USB 포트·케이블 교체 후
2 Mbps 재시험 ③ 모터 구동 중 vs 정지 중 2 Mbps 손실률 비교(PWM EMI 판정) ④ 09-06 펌웨어 A/B.

**소급 영향**: 09-08 의 미해결 이상(1.40 m 목표에 5.79 m 경로, SLAM map yaw 점프,
여유가 있는데 상자에 붙는 경로)이 odom 간헐 소실의 약한 증상이었을 가능성이 있다.
당시 코스트맵 파라미터로 설명했는데, 그 설명이 전부 틀렸다는 뜻은 아니지만 **오염 가능성은 인정한다.**
링크가 안정된 지금 재검증이 필요하다.

## 9. 이 날 배운 것

1. **"잘 맞아떨어지는 숫자" 하나로 인과를 단정하지 말 것.** USB 32 B 엔드포인트에서 계산한
   32~40 kB/s 가 관측 최대치 36.6 kB/s 와 일치해서 확신했지만, 그건 우연이었다.
   과거 로그(60 kB/s)를 5 분만 확인했으면 즉시 반증됐을 것이다.
   **새 이론을 세우면 과거 측정치와 먼저 대조한다.**
2. **"어제까지 됐다"는 정보는 가설을 절반으로 줄인다.** 사용자의 질의가 없었으면 나는 잘못된
   용량 한계 이론을 그대로 커밋해 두었을 것이다. 회귀인지 한계인지부터 가르는 것이 순서다.
3. **best-effort 는 실패를 알려주지 않는다.** `rcl_publish` 가 rc=0 을 돌려주는데도 데이터가
   사라졌다. 계층별 계측(rcl / 전송 / agent / DDS)을 넣어 구간을 좁히기 전까지는
   모든 가설이 그럴듯해 보였다. **계측 없는 추론은 비용만 든다.**
4. **부분 실패는 크기 순으로 온다.** 작은 메시지가 정확한 주기를 유지하는데 큰 메시지만 사라지는
   비대칭이 원인 구간을 좁히는 가장 강한 단서였다.
5. **도구의 정규식 방언을 확인할 것.** `pkill -f "a\|b"` 는 ERE 에서 리터럴이다. 정리 스크립트가
   조용히 실패해 측정 두 건을 오염시켰다.
